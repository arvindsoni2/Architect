Architecture from first principles

Strip away products, frameworks and pattern names, and every system in this handbook rests on four truths. Each chapter’s first-principles block names the problem it solves and which of compute, data and communication it acts on.

First principleWhat it means
Every system is compute, data and communication.From a to-do app to a stock exchange you arrange the same three things. Learn how each behaves under load and failure, and the patterns become variations.
Everything is a trade-off.Mark Richards’ first law of software architecture: there is no best practice, only a choice that fits this context. Always say what you give up.
Architecture exists to manage complexity and change.The job is to control what changes, how often and at what cost. Choosing technology comes second.
Quality attributes are the real deliverables.Features say what the system does. Latency, availability, consistency and cost say whether it holds up.

Implication: you don’t need fifty patterns. You need to know how compute, data and communication behave under load and failure.

Start With Requirements, Not Components

First principles

The problem it solves: Teams build the wrong system when nobody has said what “good” means in numbers.

Irreducible truthSo what
Every architecture choice answers a force: a quality attribute, a constraint or a risk.If you can’t name the force behind a box, remove the box or find the force.
Functional requirements rarely shape the architecture; quality attributes do.Redirecting a URL is easy. Doing it in 50 ms at 100K requests/s for five years is the design problem.
An attribute you can’t measure can’t be traded off.Turn “fast” into “p95 under 50 ms at peak” so it can be tested and argued about.
Scope is a cost.Each non-goal you write down removes components you would otherwise build.

Pareto · learn this first

The 20% (learn now)

  • Separate what the system does from how well it must do it.
  • Write each quality attribute as a measurable scenario: load, response, measure.
  • List non-goals explicitly.

Defer (second pass)

  • Utility trees and formal evaluation workshops (ATAM).
  • Detailed cost and compliance mapping; return to it for regulated systems.
  • Stakeholder-mapping techniques beyond a simple list.
System design starts by turning an ambiguous product idea into a bounded contract. Separate functional requirements (what the system must do) from quality attributes (how well it must do it), constraints, assumptions, and explicit non-goals.

Core mental model: architecture is a response to forces. If the forces are vague, the design is guesswork.

Example — URL shortener. Functional: create a short URL and redirect it. Quality attributes: p95 redirect latency < 50 ms, 99.99% availability, 100M stored mappings, links retained for 5 years. Non-goal: real-time analytics in v1.

Deliberate practice

  1. Write 5 functional requirements and 5 non-functional requirements for a food-delivery app.
  2. Convert “fast”, “highly available” and “secure” into measurable scenarios.
  3. List 3 non-goals that prevent scope creep.

Design challenge

Given a chat application, explain which requirement would change your architecture most: 10K users, 10M users, end-to-end encryption, or 7-year message retention — and why.

“Fast” gives no target, so nobody can test it or say when a design is good enough. Write who does what, under what load, and the measured result: “At 100K redirects per second, 95% of redirects finish within 50 ms, measured at the load balancer.” That one sentence already implies a cache, servers that can be added freely and a capacity estimate. Then write what you will not build in v1, such as real-time analytics, so the design stays small enough to finish.

Capacity Estimation & Bottleneck Thinking

First principles

The problem it solves: You must choose components before the system exists, so you need numbers good enough to find the first bottleneck.

Acts on: compute data communication

Irreducible truthSo what
Load is people × actions × time.Daily volume ÷ 86,400 gives the average; a peak factor gives what you design for.
Every request spends CPU, memory, disk I/O and network.Multiply the cost of one request by peak load; the resource that runs out first is the bottleneck.
Orders of magnitude decide architecture; decimals don’t.231 or 250 requests/s changes nothing. 2.3K or 230K changes everything.
An estimate is only as good as its stated assumptions.Write each assumption beside its number so it can be challenged.

Pareto · learn this first

The 20% (learn now)

  • Average = daily requests ÷ 86,400; design for average × peak factor.
  • Storage = writes/day × bytes × retention × replication.
  • Find the first resource to saturate: bandwidth, IOPS, CPU or memory.

Defer (second pass)

  • Memorising detailed latency tables beyond rough orders of magnitude.
  • Precise cloud pricing and cost models.
  • Queueing models; chapter 03 covers Little’s Law.
Back-of-envelope estimation is not fortune-telling. It turns scale into orders of magnitude so you can identify likely bottlenecks.

Estimate requests/sec, read:write ratio, payload size, daily storage growth, retention, bandwidth, concurrency, and peak multiplier. State every assumption.

Average QPS = daily requests ÷ 86,400
Peak QPS = average QPS × assumed peak factor
Storage/year = writes/day × bytes/write × 365 × replication factor
Example. 20M image views/day ≈ 231 average views/sec. With a 10× peak factor, design around ~2.3K views/sec before cache/CDN effects. The number is useful because the assumption is visible.
From numbers to machines and memory. Say 50M daily users make 20 reads each: 1B reads a day ≈ 11.6K a second, or ≈ 58K at a 5× peak. If load tests show one instance serves about 2K of these requests a second (measure it; this varies tenfold between workloads), you need about 30 instances at peak. To survive losing one of three zones, the other two must carry the peak: 15 per zone, 45 in total. If 20% of 1B items take 80% of reads, cache that 20%: 200M × 1 KB ≈ 200 GB across several cache nodes. Storage: 2M writes a day × 2 KB ≈ 4 GB a day ≈ 1.5 TB a year raw, ≈ 4.4 TB with three replicas, before indexes and backups.

Deliberate practice

  1. Estimate peak QPS for 50M API calls/day using 5× and 20× peak factors.
  2. Estimate storage for 5M 2-KB records/day retained for 3 years with 3× replication.
  3. Name the first measurement you would validate in production.

Design challenge

    Banned words: QPS, throughput, bottleneck
  3. Gap hunt. If you stumbled, reread only that part:
    • Mixed up average and peak: reread the two formulas at the top of the chapter.

Model answer (open after you have tried)

How much one server can handle depends on what each request does. Returning a cached 1 KB value takes very little CPU, so tens of thousands per second is plausible. Building a report that reads 50 MB from disk, or calls three other services, might allow only hundreds per second on the same machine. Payload size, CPU work, disk reads and time spent waiting on other services all change the answer. Estimate the cost of one request first, multiply by the peak load, and see which resource runs out.

Latency, Throughput & Little’s Law

First principles

The problem it solves: Users wait for the slowest part of every request, and averages hide the slow ones.

Acts on: compute communication

Irreducible truthSo what
Work in progress = arrival rate × time in system (Little’s Law).If time in system doubles, you need twice the threads, connections and memory for the same load.
Throughput and latency measure different things.A system can serve 10K requests/s while 1% of users wait three seconds.
Queues grow sharply as arrivals approach capacity.Near full utilisation a small load increase causes a large latency increase, so keep headroom.
Latencies add along a path, and fan-out exposes the slowest call.A request that calls 20 services hits one of their slow responses far more often than a single call does.

Pareto · learn this first

The 20% (learn now)

  • L = λ × W, and what it means for pool and thread sizes.
  • Design and alert on p95/p99, not averages.
  • Utilisation near 100% makes waiting time explode.

Defer (second pass)

  • Formal queueing models such as M/M/1.
  • Benchmarking pitfalls such as coordinated omission.
  • Tail-latency techniques such as hedged requests.
Latency and throughput are different. A system can have high throughput and poor tail latency. Users often experience the tail, so design around percentiles such as p95/p99 rather than averages.

Little’s Law: in a stable system, average concurrency ≈ throughput × average time in system.

L = λW
Example: 2,000 requests/sec × 0.2 sec ≈ 400 concurrent in-flight requests

Queues, locks, GC pauses, network hops, cold starts and downstream calls often dominate tail latency.

Deliberate practice

  1. For 8K RPS and 150 ms average latency, estimate concurrency.
  2. Explain why adding a queue may improve reliability but worsen end-to-end latency.
  3. Identify three places where p99 latency can appear in a request path.

Design challenge

A service has 20 ms database latency but 800 ms p99 API latency. Sketch a debugging hypothesis tree.

  1. Blank page. Draw the path from arrivals to response, mark where waiting happens, and write λ, W and L where they belong.
  2. Explain it to a junior. Explain how the API’s slowest 1% of requests can take 800 ms when the database answers in 20 ms.
    Banned words: p99, percentile, Little’s Law
  3. Gap hunt. If you stumbled, reread only that part:
    • Couldn’t compute in-flight requests: reread the 2,000 × 0.2 example.
    • Couldn’t name where the time goes: go back to step 2 (waiting for a worker).
    • Mixed up throughput and latency: reread the first paragraph.
Model answer (open after you have tried)

The database is only one stop. A request can wait for a free worker, wait for a database connection from a pool, pause while the runtime cleans up memory, call other services, or retry after a timeout. These delays hit some requests and not others, so the average looks fine while the slowest few are slow. Trace slow requests and split their time into waiting, own work and each downstream call. Then check whether a pool is smaller than the number of requests in flight that the arrival rate and time in system imply.

Horizontal Scaling, Statelessness & Load Balancing

First principles

The problem it solves: One machine has a ceiling and is a single point of failure.

Acts on: compute communication

Irreducible truthSo what
You can add machines freely only if any machine can serve any request.Keep request-serving code free of local state; put state in stores built for it.
State does not disappear; it moves.Sessions go to a shared store, files to object storage, truth to the database. Each needs its own scaling plan.
A load balancer is only as good as its health checks.Routing traffic to a sick instance spreads the failure.
Capacity must survive losing part of itself.If 20% of instances fail at peak, the rest must carry the load or shed it.

Pareto · learn this first

The 20% (learn now)

  • Stateless application tier behind a load balancer.
  • External session store instead of sticky sessions.
  • Health checks and spare capacity for lost instances.

Defer (second pass)

  • Algorithms beyond round-robin and least-connections.
  • Anycast and global traffic-management details.
  • Autoscaling policy tuning.
Horizontal scaling adds instances; vertical scaling adds capacity to one instance. Horizontal scaling is usually easier when request-serving compute is stateless.

State still exists — move authoritative state to appropriate stores rather than pretending it disappears.

Load balancing choices. Round-robin is simple; least-connections can help uneven request duration; consistent hashing is useful when affinity or distributed ownership matters. Health checks and overload handling matter as much as the algorithm.

Deliberate practice

  1. Turn a stateful web session design into a horizontally scalable version.
  2. Compare sticky sessions with external session storage.
  3. Explain what happens when 20% of instances fail during peak traffic.

Design challenge

Design the request path for a global read-heavy API using DNS/Anycast, regional load balancers and stateless application instances.

  1. Blank page. Draw client, DNS, load balancer, three instances, session store and database. Number the five steps and mark which boxes hold state.
  2. Explain it to a junior. Explain why sticky sessions make scaling and failure harder than a shared session store.

  3. Gap hunt. If you stumbled, reread only that part:

    • Couldn’t explain what happens when an instance dies: step 5 and the 20%-failure exercise.
    • Unsure when one bigger machine is fine: reread the first paragraph.
Model answer (open after you have tried)

With sticky sessions, each user is tied to one server because their session lives in that server’s memory. If the server dies, its users lose their sessions. New servers get no existing users, so load stays uneven, and taking a server out for a deploy logs people out. With sessions in a shared store, any server can handle any request, so you can add, remove or replace servers freely and the load balancer can spread load evenly. The cost is one extra network call per request, and the store now needs its own replication.

Caching: Placement, Policy & Invalidation

First principles

The problem it solves: The same data is read far more often than it changes, and the source of truth is slow or expensive to ask.

Acts on: data communication

Irreducible truthSo what
A cache is a copy, and every copy can be wrong.Choose how stale is acceptable per data type. A product description and a bank balance get different answers.
Caching only pays when reads repeat.Hit rate decides the design. Cache hot keys, not everything.
The database is usually sized for the cache’s misses.If the cache empties, the full read load lands on a database never built for it. That is a stampede.

Pareto · learn this first

The 20% (learn now)

  • Cache-aside read path and delete-on-write.
  • TTL with random jitter as the default freshness control.
  • Stampedes, and request coalescing as the fix.

Defer (second pass)

  • Write-through and write-behind; return after chapter 11.
  • Eviction policies beyond LRU.
  • Negative caching and versioned keys; meet them in lab L02.
Caching trades freshness and complexity for latency, throughput and cost. Decide what to cache, where, for how long, and how it becomes correct again.

Common layers: browser/device → CDN/edge → reverse proxy → application cache → database buffer/index caches.

Cache-aside. Read cache → on miss read database → populate cache. It is simple, but stale reads, cache stampedes and invalidation must be designed.

Useful controls include TTLs, versioned keys, request coalescing, negative caching and jittered expiries.

Write policyHow it worksMain risk
Write-throughwrite the store and the cache togetherslower writes; if one of the two writes fails they disagree
Write-aroundwrite only the store; the cache fills on the next read missfirst read after a write is a miss
Write-behindwrite the cache; persist to the store laterdata loss and reordering if the cache fails first
Refresh-aheadreload popular keys shortly before they expirewasted work on keys nobody reads again

Eviction. When memory is full the cache drops something: least recently used (LRU) suits most read paths; least frequently used (LFU) protects steady favourites from one-off scans. Size the cache from the hot set (chapter 2), and watch hit rate and evictions per second, not just memory.

Deliberate practice

  1. Choose a cache strategy for product catalogue, bank balance and feature flags.
  2. Explain cache stampede and two mitigations.
  3. Design invalidation after a product price changes.

Design challenge

Model answer (open after you have tried)

Updating the cache on a write can race with a read that started earlier: a slow reader can put the old price back after you wrote the new one. Deleting the key means the next reader fetches the fresh value from the database. A short window remains where a reader may still hold the old value, which is acceptable for a product price and not for a balance. If a popular key expires and thousands of requests miss at once, they all hit the database; coalescing lets one request refill the key while the others wait for it.

Partitioning, Sharding & Consistent Hashing

First principles

The problem it solves: One database node can’t hold all the data or serve all the traffic.

Acts on: data compute

Irreducible truthSo what
The partition key decides where each row lives and which queries stay on one node.Pick it from your most important access pattern.
Load follows popularity, not row counts.Equal-sized shards can still have one hot shard. Plan for hot keys.
Moving data is expensive.Prefer schemes that move only a small fraction of keys when nodes change.
Queries and transactions across partitions cost coordination.If a common query touches every shard, the key is wrong for it.

Pareto · learn this first

The 20% (learn now)

  • Choose the partition key from access patterns.
  • Hash vs range partitioning trade-off.
  • Hot keys and their mitigations.

Defer (second pass)

  • Directory-based routing internals.
  • Online resharding procedures.
  • Transactions that span shards.
Partitioning divides data or work so it can scale. Good partition keys distribute load while preserving the access patterns you need.

Range partitioning supports scans but can hotspot. Hash partitioning balances better but makes range access harder. Directory-based routing is flexible but adds metadata dependency.

Hot-key problem. Partitioning social posts by celebrity_id can overload one shard. Mitigations may include key salting, read caching, fan-out strategies or separating hot entities.

Deliberate practice

  1. Pick partition keys for telemetry events, user profiles and orders.
  2. Explain rebalancing when nodes are added.
  3. Show why consistent hashing reduces remapping compared with modulo hashing.

Design challenge

Model answer (open after you have tried)

With remainder-of-division, a key’s server is its hash divided by the number of servers, keeping the remainder. Change the number of servers from 4 to 5 and almost every remainder changes, so most keys move. On a ring, each server owns the stretch of the ring just before its position. A new server takes over part of one neighbour’s stretch, so only those keys move, roughly one fifth. Giving each server many small positions spreads both the load and the moved keys evenly.

Replication, Quorums & Consistency

First principles

The problem it solves: One copy of data can be lost, is slow for distant users and can’t serve every read.

Acts on: data communication

Irreducible truthSo what
Copies take time to agree.Every read from a copy must accept possibly old data or pay to check.
Waiting for a second copy buys durability with latency.Synchronous replication adds a round trip to every write.
Ordering needs one place that decides.A single leader orders writes simply; several writers need a conflict policy.
Consistency words name different guarantees.Linearizable, serializable, snapshot and eventual are not synonyms. Say which one the operation needs.

Pareto · learn this first

The 20% (learn now)

  • Leader/follower with synchronous and asynchronous followers.
  • Replication lag and read-your-writes.
  • R + W > N as overlap reasoning, not a guarantee on its own.

Defer (second pass)

  • Multi-leader and leaderless conflict resolution (vector clocks, CRDTs).
  • Consensus protocols such as Raft.
  • Isolation levels in depth.
Replication improves availability, read scale and durability, but introduces coordination and consistency questions.

Leader/follower replication simplifies ordering but introduces leader failover. Multi-leader and leaderless approaches can improve locality or availability while increasing conflict-handling complexity.

For N replicas, quorum-style reasoning often uses R + W > N to create overlap — but actual guarantees depend on the datastore’s protocol, failure model and consistency semantics.

Always distinguish linearizability, serializability, snapshot isolation, causal consistency and eventual convergence; they are not synonyms.

Deliberate practice

  1. Explain read-your-writes and monotonic reads using a social profile update.
  2. Compare synchronous vs asynchronous replication.
  3. Identify which operations in a bank require stronger consistency than a social feed.

First principles

The problem it solves: Networks lose acknowledgements, so senders retry and receivers see the same message twice.

Acts on: communication data

Irreducible truthSo what

Idempotency keys, done properly. Scope the key to the caller and the operation (account + endpoint), not globally. Store the key with a fingerprint of the request and the response you returned. First principles

Below every database choice sits a storage engine. Two families cover most of what you will meet.

B-tree. Keys are kept sorted in fixed-size pages (often 4–16 KB) arranged as a shallow tree, so a lookup reads three or four pages. A change is first appended to the write-ahead log (WAL), then the page is rewritten in place. Point reads, range scans and transactions are cheap; many small random writes are expensive because each one dirties a whole page.

LSM tree (log-structured merge). A write goes to the WAL and into an in-memory sorted table (the memtable). When the memtable fills, it is flushed to disk as an immutable sorted file (an SSTable). Background compaction merges files and throws away overwritten values and deletion markers (tombstones). Writes are sequential and fast. A read may have to check the memtable and several files, so each file keeps a Bloom filter that answers “definitely not here” without touching the disk.

Interview use. “Two million sensor writes a second, rarely updated, read by time range” points to an LSM-based wide-column or time-series store, and you should mention compaction cost. “Orders with constraints and joins” points to a B-tree relational database. Across services. Consensus, Leader Election, Leases & Fencing

First principles

The problem it solves: Several machines must agree on one fact (who leads, which write came first, who holds a lock) even when some crash or the network splits.

Consensus lets a group of nodes agree on an ordered log of decisions, so every node applies the same changes in the same order (a replicated state machine). Raft, used by etcd and Consul, splits the problem into leader election, log replication and safety. A leader is elected for a numbered term by a majority vote; it appends entries to its log and treats an entry as committed once a majority has stored it.
Failures tolerated = ⌊(N − 1) ÷ 2⌋ → 3 nodes: 1 · 4 nodes: 1 · 5 nodes: 2 · 7 nodes: 3

Spread members across failure domains (zones). Larger clusters tolerate more failures but every write waits for more acknowledgements, so five is a common ceiling.

You rarely implement this yourself. Use a coordination service (etcd, ZooKeeper, Consul) or a database that embeds consensus, and design what your service does when it loses its lease: stop writing, step down, and let the new leader take over.

Why leases need fencing. Worker A takes a lock with a 10-second lease, then freezes for 15 seconds in garbage collection. The lease expires and worker B takes the lock. A wakes up and writes, still believing it holds the lock. The fix is a fencing token: the lock service hands out an increasing number with every grant (33 to A, 34 to B), and the storage remembers the highest number it has accepted and rejects anything lower. A lock without fencing is fine for efficiency (avoiding duplicate work) but not for correctness.

Split brain is two nodes both acting as leader. Majority voting stops two leaders being elected for the same term; fencing stops a deposed leader’s late writes from landing.

Change data capture reads the database’s own change log and publishes every insert, update and delete as an event. Unlike “write to the database and also publish an event”, it can’t miss a change, because it reads what was actually committed.

Time and windows. Event time is when something happened; processing time is when you saw it. Mobile clients go offline, so a click from 10:01 may arrive at 10:09. Windows group events by event time: tumbling (fixed, non-overlapping, e.g. per minute), sliding (overlapping, e.g. last 5 minutes every minute) or session (closed by a gap of inactivity). A watermark is the processor’s estimate that “all events up to time T have probably arrived”; when it passes the end of a window, the result is emitted. Events later than that are dropped, sent to a correction path, or used to update the result.

Restarts. Stream processors checkpoint their state and input offsets. “Exactly once” inside a processor holds only if the output is written transactionally with the checkpoint, or the output is an upsert keyed by (key, window) so a replay replaces instead of adding.

Ad-click aggregation. Clicks flow into a partitioned log. A stream job counts clicks per ad per one-minute event-time window, waits two minutes for late clicks, then upserts counts into an OLAP store keyed by (ad, minute). Dashboards read those counts within seconds. A nightly batch recomputes yesterday from the raw log and corrects any drift, and billing uses the batch numbers. Fast numbers for people; exact numbers for money.

Safe Change: Schema Migration, Compatibility & Progressive Delivery

First principles

The problem it solves: Production systems must change code, schemas and contracts while old and new versions run side by side.

Acts on: data communication

Irreducible truthSo what
During any rollout, old and new code run at the same time against the same data.Every schema and message change must work with both versions.
A change that can’t be rolled back must be split until each step can.Expand, migrate, contract: never rename or repurpose in one step.
Most incidents start with a change.Release to a small slice first and widen only while service-level signals stay healthy.
Deploying code and releasing behaviour are separate decisions.Use feature flags to release, and remove them when done.

Pareto · learn this first

The 20% (learn now)

  • Expand → migrate (backfill, dual write, switch reads) → contract.
  • Compatible APIs and events: add optional fields, never change a field’s meaning.
  • Canary releases with automatic rollback on SLO signals; flags to separate release from deploy.

Defer (second pass)

  • Online schema-change tools (gh-ost, pg_repack).
  • Schema registries and compatibility modes for event streams.
  • Blue-green cut-overs for very large data migrations.
Rename a column without downtime (phone → mobile_number):
  1. Expand. Add mobile_number as nullable. Deploy code that writes both columns and still reads phone.
  2. Backfill. Copy existing rows in small, throttled batches that are safe to re-run.
  3. Switch reads. Deploy code that reads mobile_number, behind a flag; compare results for a while.
  4. Contract. Stop writing phone; after the rollback window has passed, drop it.

Each step can be deployed and rolled back on its own. Doing it in one migration breaks every instance still running the old code during the rollout.

Compatibility rules. Add optional fields; never change a field’s type or meaning in place; readers ignore fields they don’t know; version an API only when you must break it, and run both versions until consumers have moved. Events in a log may be replayed months later, so event schemas need the same discipline as public APIs.

Progressive delivery. A canary sends 1%, then 5%, 25% and 100% of traffic to the new version, comparing its error rate and latency against the old one, and rolls back automatically if they diverge. Blue-green keeps two full environments for an instant switch, but they usually share one database, which is why expand/contract still matters.

Interview move. When you propose a new data model or split a service, add one sentence: “We’d migrate with expand and contract plus a backfill, behind a flag, so every step can be rolled back.” It shows you have shipped changes to live systems.

Deliberate practice

  1. Plan expand/contract for splitting a name column into first_name and last_name.
  2. Classify five API changes as compatible or breaking (add field, remove field, rename field, new enum value, stricter validation).
  3. Choose canary metrics and thresholds for a checkout service.

URL Shortener

Design brief. 100M links, 100K redirect RPS peak, p95 <50 ms. Separate redirect correctness from asynchronous analytics.

Primary muscles: Estimation · key generation · cache · redirects · analytics

Worked solution sketch: URL shortener (open after you have tried it)

One reasonable design, with its assumptions visible. Yours may differ; defend the trade-offs.

  1. Estimate. 100K redirect req/s at peak; assume about 1K creates/s. 100M mappings × ~500 bytes ≈ 50 GB before replication — one replicated key-value cluster is enough; partition by short code when it grows.
  2. Key generation. Encode a unique 64-bit ID in base62; seven characters give about 3.5 trillion codes. Avoid hashing the long URL directly unless you handle collisions.
  3. Hot path. Redirects are read-heavy and cacheable: CDN for popular links, an in-memory cache in front of the store, stateless redirect servers behind the load balancer. Choose 301 vs 302 deliberately — 301 lets browsers cache and hides clicks from analytics.
  4. Analytics stays off the hot path. Emit a click event to a queue after responding; losing an analytics event must never fail a redirect.
  5. Failure. If the store is slow, serve cached codes and fail closed for unknown ones; rate-limit creation to stop abuse; expire links per the retention policy.

Reusable system-design review checklist

QuestionWhat a strong answer contains
What are we designing?Actors, use cases, non-goals, measurable quality attributes.
How large is it?Assumptions, QPS, payloads, storage, bandwidth, peak factor.
Where is state?Source of truth, data model, indexes, partition key, replication.
What must be consistent?Business invariants and operation-specific consistency.
What is synchronous?Latency budget, dependencies, timeouts, idempotency.
What is asynchronous?Queue/stream semantics, ordering, retries, duplicates, DLQ.
How does it fail?Dependency, node, AZ, region, slow failure, overload, data corruption.
How is blast radius limited?Bulkheads, circuit breakers, rate limiting, shedding, cells/regions.
How do we know it works?SLIs, SLOs, traces, metrics, logs, synthetic tests, error budgets.
How does it evolve?ADRs, backward-compatible contracts, expand/contract migrations, progressive rollout, rollback, ownership.
Who can do what?Trust boundaries, authentication, object-level authorisation, tenant isolation, keys, residency, audit.
What does it cost?Unit cost per request or user, the biggest driver, and the design choice that moves it.
