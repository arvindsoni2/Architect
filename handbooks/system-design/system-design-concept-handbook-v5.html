Part I · Core concepts and building blocks

01
Foundations

Start With Requirements, Not Components

System design starts by turning an ambiguous product idea into a bounded contract. Separate functional requirements (what the system must do) from quality attributes (how well it must do it), constraints, assumptions, and explicit non-goals.

Core mental model: architecture is a response to forces. If the forces are vague, the design is guesswork.

Example — URL shortener. Functional: create a short URL and redirect it. Quality attributes: p95 redirect latency < 50 ms, 99.99% availability, 100M stored mappings, links retained for 5 years. Non-goal: real-time analytics in v1.

Deliberate practice

  1. Write 5 functional requirements and 5 non-functional requirements for a food-delivery app.
  2. Convert “fast”, “highly available” and “secure” into measurable scenarios.
  3. List 3 non-goals that prevent scope creep.

Design challenge

Given a chat application, explain which requirement would change your architecture most: 10K users, 10M users, end-to-end encryption, or 7-year message retention — and why.

Recall check

Without looking back, explain Start With Requirements, Not Components in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

02
Foundations

Capacity Estimation & Bottleneck Thinking

Back-of-envelope estimation is not fortune-telling. It turns scale into orders of magnitude so you can identify likely bottlenecks.

Estimate requests/sec, read:write ratio, payload size, daily storage growth, retention, bandwidth, concurrency, and peak multiplier. State every assumption.

Average QPS = daily requests ÷ 86,400
Peak QPS = average QPS × assumed peak factor
Storage/year = writes/day × bytes/write × 365 × replication factor
Example. 20M image views/day ≈ 231 average views/sec. With a 10× peak factor, design around ~2.3K views/sec before cache/CDN effects. The number is useful because the assumption is visible.

Deliberate practice

  1. Estimate peak QPS for 50M API calls/day using 5× and 20× peak factors.
  2. Estimate storage for 5M 2-KB records/day retained for 3 years with 3× replication.
  3. Name the first measurement you would validate in production.

Design challenge

Why is “a server handles 50K QPS” a poor system-design assumption? Give four workload variables that can change the answer.

Recall check

Without looking back, explain Capacity Estimation & Bottleneck Thinking in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

03
Foundations

Latency, Throughput & Little’s Law

Latency and throughput are different. A system can have high throughput and poor tail latency. Users often experience the tail, so design around percentiles such as p95/p99 rather than averages.

Little’s Law: in a stable system, average concurrency ≈ throughput × average time in system.

L = λW
Example: 2,000 requests/sec × 0.2 sec ≈ 400 concurrent in-flight requests

Queues, locks, GC pauses, network hops, cold starts and downstream calls often dominate tail latency.

Deliberate practice

  1. For 8K RPS and 150 ms average latency, estimate concurrency.
  2. Explain why adding a queue may improve reliability but worsen end-to-end latency.
  3. Identify three places where p99 latency can appear in a request path.

Design challenge

A service has 20 ms database latency but 800 ms p99 API latency. Sketch a debugging hypothesis tree.

Recall check

Without looking back, explain Latency, Throughput & Little’s Law in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

04
Scale

Horizontal Scaling, Statelessness & Load Balancing

Horizontal scaling adds instances; vertical scaling adds capacity to one instance. Horizontal scaling is usually easier when request-serving compute is stateless.

State still exists — move authoritative state to appropriate stores rather than pretending it disappears.

Load balancing choices. Round-robin is simple; least-connections can help uneven request duration; consistent hashing is useful when affinity or distributed ownership matters. Health checks and overload handling matter as much as the algorithm.

Deliberate practice

  1. Turn a stateful web session design into a horizontally scalable version.
  2. Compare sticky sessions with external session storage.
  3. Explain what happens when 20% of instances fail during peak traffic.

Design challenge

Design the request path for a global read-heavy API using DNS/Anycast, regional load balancers and stateless application instances.

Recall check

Without looking back, explain Horizontal Scaling, Statelessness & Load Balancing in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

05
Scale

Caching: Placement, Policy & Invalidation

Caching trades freshness and complexity for latency, throughput and cost. Decide what to cache, where, for how long, and how it becomes correct again.

Common layers: browser/device → CDN/edge → reverse proxy → application cache → database buffer/index caches.

Cache-aside. Read cache → on miss read database → populate cache. It is simple, but stale reads, cache stampedes and invalidation must be designed.

Useful controls include TTLs, versioned keys, request coalescing, negative caching and jittered expiries.

Deliberate practice

  1. Choose a cache strategy for product catalogue, bank balance and feature flags.
  2. Explain cache stampede and two mitigations.
  3. Design invalidation after a product price changes.

Design challenge

Your cache hit rate falls from 95% to 60% after a deploy. What system-level effects do you expect, and what would you inspect first?

Recall check

Without looking back, explain Caching: Placement, Policy & Invalidation in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

06
Data

Partitioning, Sharding & Consistent Hashing

Partitioning divides data or work so it can scale. Good partition keys distribute load while preserving the access patterns you need.

Range partitioning supports scans but can hotspot. Hash partitioning balances better but makes range access harder. Directory-based routing is flexible but adds metadata dependency.

Hot-key problem. Partitioning social posts by celebrity_id can overload one shard. Mitigations may include key salting, read caching, fan-out strategies or separating hot entities.

Deliberate practice

  1. Pick partition keys for telemetry events, user profiles and orders.
  2. Explain rebalancing when nodes are added.
  3. Show why consistent hashing reduces remapping compared with modulo hashing.

Design challenge

Design a sharding scheme for a multi-tenant SaaS where one tenant generates 35% of all traffic.

Recall check

Without looking back, explain Partitioning, Sharding & Consistent Hashing in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

07
Data

Replication, Quorums & Consistency

Replication improves availability, read scale and durability, but introduces coordination and consistency questions.

Leader/follower replication simplifies ordering but introduces leader failover. Multi-leader and leaderless approaches can improve locality or availability while increasing conflict-handling complexity.

For N replicas, quorum-style reasoning often uses R + W > N to create overlap — but actual guarantees depend on the datastore’s protocol, failure model and consistency semantics.

Always distinguish linearizability, serializability, snapshot isolation, causal consistency and eventual convergence; they are not synonyms.

Deliberate practice

  1. Explain read-your-writes and monotonic reads using a social profile update.
  2. Compare synchronous vs asynchronous replication.
  3. Identify which operations in a bank require stronger consistency than a social feed.

Design challenge

A user updates their password and is immediately routed to another region. Which consistency guarantee matters and how would you provide it?

Recall check

Without looking back, explain Replication, Quorums & Consistency in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

08
Data

CAP & PACELC Without the Mythology

CAP says that when a network partition prevents communication, a distributed system cannot simultaneously guarantee the theorem’s definitions of consistency and availability for the affected operations. It is not “pick any two forever.”

PACELC adds the everyday question: if there is no partition, replicated systems still trade latency against consistency.

Architectural use. For a “like” counter, accepting temporary divergence may be fine. For allocating the final airline seat, an invariant may require coordination even if that costs latency or availability.

Deliberate practice

  1. Classify three operations in e-commerce by tolerance for stale data.
  2. Explain why CAP availability differs from a marketing claim of “99.99% availability”.
  3. Write one invariant that requires coordination.

Design challenge

During a cross-region partition, should checkout, product browsing, reviews and loyalty points behave the same way? Design per-operation behavior.

Recall check

Without looking back, explain CAP & PACELC Without the Mythology in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

09
Data

Database Selection by Access Pattern

Choose data stores from access patterns, invariants and operations — not from product categories.

Ask: What are the primary keys? Query shapes? Transaction boundaries? Ordering needs? Cardinality? Update frequency? Retention? Search requirements? Analytical scans?

Polyglot persistence is a cost. PostgreSQL plus Redis plus OpenSearch can be justified, but every additional store adds backup, observability, security, consistency and skill overhead.

Deliberate practice

  1. Choose storage for orders, session tokens, full-text search, metrics and graph relationships.
  2. For each choice, name one reason not to use it.
  3. Redesign a system using fewer storage technologies.

Design challenge

Why might PostgreSQL + indexes + JSONB + pgvector be a better v1 than four specialised databases? When would you split them later?

Messaging

Queues, Streams & Asynchronous Work

Asynchrony decouples time: producers can continue without waiting for all downstream work. It improves load absorption and independence, but introduces delay, duplicates, reordering and operational state.

Queue usually models work to be consumed; log/stream models an ordered history that multiple consumers can independently process.

Queue-based load leveling. A checkout API accepts an order, persists it, and places work onto a durable queue. Workers process payment/fulfilment at a sustainable rate rather than forcing the API to synchronously absorb every downstream spike.

Deliberate practice

  1. Choose queue vs stream for email jobs, audit events and clickstream analytics.
  2. Explain consumer lag and backpressure.
  3. Design a dead-letter policy that does not become a data graveyard.

Design challenge

Traffic spikes 50× for 10 minutes. Show how a queue protects the database, and calculate the backlog drain time under two worker capacities.

Recall check

Without looking back, explain Queues, Streams & Asynchronous Work in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

11
Messaging

Delivery Semantics, Idempotency & the Outbox

Distributed messaging commonly produces duplicates. “Exactly once” is often a scoped property provided by a particular platform or transaction boundary, not a magic end-to-end guarantee.

Build consumers so repeated delivery produces the same externally visible result. Use idempotency keys, uniqueness constraints, processed-event records, or naturally idempotent state transitions.

Transactional outbox. Write business state and an outbox record in one database transaction; a relay publishes the outbox to the broker. This closes the classic “DB committed but event publish failed” gap.

Deliberate practice

  1. Make a payment-create API idempotent.
  2. Draw the dual-write failure window without an outbox.
  3. Design retry behavior when a consumer crashes after committing but before acknowledging.

Design challenge

Can you guarantee that a customer is charged exactly once? Distinguish message delivery, processing and external side effects.

Recall check

Without looking back, explain Delivery Semantics, Idempotency & the Outbox in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

12
Interfaces

API Design & Synchronous Communication

Protocol choice follows interaction shape. REST/HTTP is broadly interoperable; gRPC offers strongly typed RPC and streaming; GraphQL gives clients flexible data selection; asynchronous APIs/events decouple producers and consumers in time.

Avoid simplistic rules such as “REST public, gRPC internal.” Consider client ecosystems, latency, streaming, schema evolution, observability, intermediaries, browser support and organisational skills.

API quality. Define resource identity, idempotency, pagination, errors, timeouts, versioning, rate limits and backwards compatibility before debating frameworks.

Deliberate practice

  1. Design create/get/list APIs for orders including pagination and idempotency.
  2. Choose REST, gRPC or events for three service interactions and justify.
  3. Design an error response that is useful without leaking internals.

Design challenge

A mobile client on poor networks needs resumable uploads and live progress. Choose protocols and explain failure recovery.

Recall check

Without looking back, explain API Design & Synchronous Communication in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

Reliability

Reliability: Timeouts, Retries, Backoff & Jitter

Every remote call can fail slowly or fail partially. Set timeouts from an end-to-end latency budget, retry only faults likely to be transient, bound retries, and use backoff with jitter to avoid synchronized retry storms.

Retries multiply load. Three layers each retrying three times can produce a large amplification against a failing dependency.

Safe retry rule. Retry reads freely only when semantics allow; retry writes only when they are idempotent or protected by an idempotency mechanism.

Deliberate practice

  1. Create a 1-second latency budget across gateway, service and database.
  2. Compute worst-case attempts for three nested layers with 3 tries each.
  3. Add retry rules to a payment workflow.

Design challenge

A dependency starts timing out because it is overloaded. Explain why immediate retries can turn degradation into an outage.

Recall check

Without looking back, explain Reliability: Timeouts, Retries, Backoff & Jitter in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

Reliability

Circuit Breakers, Bulkheads & Graceful Degradation

A circuit breaker stops repeatedly calling a dependency likely to fail. A bulkhead isolates resource pools so one failure does not consume everything. Graceful degradation keeps the most valuable functions alive.

These patterns manage blast radius; they do not repair the underlying dependency.

E-commerce. If recommendations fail, product pages should still render. If inventory confirmation fails, checkout may need to stop or enter a pending state because the invariant is more important.

Deliberate practice

  1. Define circuit states and transition signals.
  2. Partition thread/connection pools for two dependencies.
  3. Create a degradation matrix for an e-commerce homepage.

Design challenge

Which features should fail open, fail closed, or degrade when identity, recommendation, search and payment services fail?

Reliability

Rate Limiting, Load Shedding & Backpressure

Capacity protection is part of correctness. Rate limiting controls admission; load shedding rejects lower-value work during overload; backpressure tells upstream producers to slow down.

Algorithms include token bucket, leaky bucket, fixed window and sliding-window variants. Choose based on burst tolerance, fairness, distributed coordination cost and precision.

Priority shedding. During severe overload, preserve authenticated checkout and health traffic before recommendation refreshes or batch exports.

Deliberate practice

  1. Design per-user and global limits for an API.
  2. Compare token bucket with fixed window for burst traffic.
  3. Define overload signals that trigger shedding.

Design challenge

Your service can safely process 20K RPS but receives 60K RPS. Design admission control so latency does not collapse for everyone.

16
Operations

SLOs, Error Budgets & Observability

Reliability becomes actionable when expressed as user-facing indicators and objectives.

SLI: measured behavior such as successful request ratio or latency. SLO: target for that indicator. Error budget: tolerated unreliability implied by the SLO. SLA is a contractual/business commitment and should not be confused with the internal engineering target.

Correlate metrics, logs and traces; instrument boundaries; propagate request/trace identifiers; alert on symptoms and budget burn rather than every internal anomaly.

Deliberate practice

  1. Define two SLIs and SLOs for a search API.
  2. Calculate monthly error budget for 99.9% and 99.99%.
  3. Design a trace for an API → service → DB → queue path.

Design challenge

CPU is 90% but users are unaffected. Separately, p99 latency is violating the SLO while CPU is 40%. Which should page an operator and why?

Recall check

Without looking back, explain SLOs, Error Budgets & Observability in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

17
Operations

Multi-Region, Failure Domains, RPO & RTO

High availability is built by identifying failure domains and deciding how much redundancy is justified.

RPO is the maximum tolerable data loss measured in time. RTO is the maximum tolerable recovery time. These should drive replication, backup and failover design.

Trade-off. Active-active can reduce regional failover time and improve locality, but increases data-consistency, routing, testing and operational complexity. Active-passive can be simpler and cheaper but may have longer recovery.

Deliberate practice

  1. Set RPO/RTO for chat messages, bank ledger and analytics reports.
  2. Compare active-active with active-passive for a global SaaS.
  3. List five failure modes beyond “a region goes down”.

Design challenge

Design regional failure behavior for an order system: what happens to new orders, in-flight payment, inventory reservation and customer status?

Recall check

Without looking back, explain Multi-Region, Failure Domains, RPO & RTO in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

Practice

Architecture Decisions, C4 & Evolution

A system design is incomplete if nobody can understand why it exists or how it may change.

Use the C4 model for hierarchical structural views: system context, containers, components and — only when useful — code. Record consequential decisions with ADRs: context, decision, alternatives and consequences.

Prefer designs that can evolve through observable, reversible steps. Architecture fitness functions can automate important constraints such as dependency direction, latency budgets, security rules or schema compatibility.

Deliberate practice

  1. Draw C4 Context and Container views for your current practice system.
  2. Write an ADR for database choice including two rejected options.
  3. Define one automated architecture fitness function.

Design challenge

Your monolith is becoming difficult to deploy. What evidence would justify extracting a service, and what would make extraction premature?

Recall check

Without looking back, explain Architecture Decisions, C4 & Evolution in 90 seconds, name one trade-off, one failure mode, and one metric that would tell you whether your design is working.

Part III · End-to-end system design case studies

Do not memorise a finished diagram. Use the same reasoning loop every time: requirements → estimates → contracts → state → architecture → bottleneck → failure → trade-off → evolution.

Case study · Beginner

URL Shortener

Design brief. 100M links, 100K redirect RPS peak, p95 <50 ms. Separate redirect correctness from asynchronous analytics.

Primary muscles: Estimation · key generation · cache · redirects · analytics

  2. 8–15 min: estimate scale and identify the likely bottleneck.
  3. 15–25 min: define API/events and data model.
  4. 25–40 min: draw high-level architecture and critical read/write paths.
  5. 40–50 min: deep-dive the hardest component.
  6. 50–57 min: inject failures, overload and regional issues.

Reusable system-design review checklist

QuestionWhat a strong answer contains
What are we designing?Actors, use cases, non-goals, measurable quality attributes.
How large is it?Assumptions, QPS, payloads, storage, bandwidth, peak factor.
Where is state?Source of truth, data model, indexes, partition key, replication.
What must be consistent?Business invariants and operation-specific consistency.
What is synchronous?Latency budget, dependencies, timeouts, idempotency.
What is asynchronous?Queue/stream semantics, ordering, retries, duplicates, DLQ.
How does it fail?Dependency, node, AZ, region, slow failure, overload, data corruption.
How is blast radius limited?Bulkheads, circuit breakers, rate limiting, shedding, cells/regions.
How do we know it works?SLIs, SLOs, traces, metrics, logs, synthetic tests, error budgets.
How does it evolve?ADRs, compatibility, migration path, rollback, ownership.
