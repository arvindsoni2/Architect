Running the Agents

Use three runtime profiles instead of one vague command: local deterministic for unit and workflow tests with mocked models; acceptance smoke for a small live dataset with strict cost and timeout budgets; and full evidence run for release or scheduled evaluation. Every run should emit a manifest, durable run ID, trace link, partial-result policy, and resume or retry instructions.

Implementation Path: Build Scout + Forge

A runnable reference architecture that turns the curriculum into an engineering project. The labs deliberately separate domain models, provider adapters, graph orchestration, MCP transport, tests, and deployment boundaries.

Definition of done

Scout

Generates a query plan, searches with Perplexity, enriches pages with Firecrawl, pauses for source approval, and returns a validated research bundle.

Forge

Consumes only the research bundle, drafts a lesson, evaluates deterministic and model-based criteria, revises within a budget, and escalates failures.

Integration

Forge calls Scout through start/resume MCP tools rather than importing Scout internals. Each component can be tested and deployed independently.

Evidence

Every test run emits deterministic assertions; live provider tests are explicitly marked and never run accidentally in ordinary CI.

Lab 1: Expose Scout with FastMCP

Use MCP as a typed service boundary. Keep orchestration in the application layer; the MCP server should validate inputs, call the service, and serialize outputs.

Senior engineering rule: an MCP tool is an adapter, not the place to hide business logic.
src/scout/models.py
from __future__ import annotations

from datetime import UTC, datetime
from hashlib import sha256
from typing import Literal

from pydantic import BaseModel, Field, HttpUrl


class EvidenceSource(BaseModel):
    source_id: str
    title: str
    url: HttpUrl
    excerpt: str = Field(min_length=1)
    retrieved_at: datetime
    provider: Literal["firecrawl", "perplexity"]
    content_hash: str

    @classmethod
    def create(
        cls,
        *,
        title: str,
        url: str,
        excerpt: str,
        provider: Literal["firecrawl", "perplexity"],
    ) -> "EvidenceSource":
        normalized = excerpt.strip()
        digest = sha256(normalized.encode("utf-8")).hexdigest()
        return cls(
            source_id=digest[:12],
            title=title.strip() or url,
            url=url,
            excerpt=normalized,
            retrieved_at=datetime.now(UTC),
            provider=provider,
            content_hash=digest,
        )


class ResearchBundle(BaseModel):
    topic: str
    executive_summary: str
    sources: list[EvidenceSource]
    open_questions: list[str] = Field(default_factory=list)
src/scout/service.py
from __future__ import annotations

from collections.abc import Sequence
from uuid import uuid4

from langgraph.types import Command

from scout.models import EvidenceSource, ResearchBundle


class ResearchService:
    def __init__(self, graph) -> None:
        self.graph = graph

    @staticmethod
    def _config(run_id: str) -> dict:
        return {"configurable": {"thread_id": run_id}}

    @staticmethod
    def _interrupt_payloads(state: dict) -> list[object]:
        return [getattr(item, "value", item) for item in state.get("__interrupt__", ())]

    async def start(self, topic: str, max_sources: int = 8) -> dict:
        run_id = uuid4().hex
        state = await self.graph.ainvoke(
            {"topic": topic, "max_sources": max_sources},
            config=self._config(run_id),
        )
        requests = self._interrupt_payloads(state)
        if requests:
            return {
                "run_id": run_id,
                "status": "awaiting_approval",
                "approval_requests": requests,
            }
        bundle = ResearchBundle.model_validate(state["bundle"])
        return {
            "run_id": run_id,
            "status": "completed",
            "bundle": bundle.model_dump(mode="json"),
        }

    async def resume(self, run_id: str, decision: dict) -> dict:
        state = await self.graph.ainvoke(
            Command(resume=decision),
            config=self._config(run_id),
        )
        requests = self._interrupt_payloads(state)
        if requests:
            return {
                "run_id": run_id,
                "status": "awaiting_approval",
                "approval_requests": requests,
            }
        bundle = ResearchBundle.model_validate(state["bundle"])
        return {
            "run_id": run_id,
            "status": "completed",
            "bundle": bundle.model_dump(mode="json"),
        }


def dedupe_sources(items: Sequence[EvidenceSource]) -> list[EvidenceSource]:
    by_url: dict[str, EvidenceSource] = {}
    for item in items:
        by_url.setdefault(str(item.url), item)
    return list(by_url.values())

Lab 2: Build the Firecrawl Adapter

Firecrawl handles search discovery and page extraction. The adapter immediately converts vendor objects into your own EvidenceSource model so the rest of the system is provider-independent.

src/scout/providers/firecrawl_provider.py
from __future__ import annotations

from firecrawl import Firecrawl

from scout.models import EvidenceSource


class FirecrawlProvider:
    def __init__(self, api_key: str | None = None) -> None:
        self.client = Firecrawl(api_key=api_key) if api_key else Firecrawl()

    def search(self, query: str, limit: int = 5) -> list[EvidenceSource]:
        response = self.client.search(query, limit=limit)
        return [
            EvidenceSource.create(
                title=item.title or item.url,
                url=item.url,
                excerpt=getattr(item, "description", "") or item.title or item.url,
                provider="firecrawl",
            )
            for item in response.web
        ]

    def scrape(self, url: str) -> EvidenceSource:
        result = self.client.scrape(url)
        metadata = result.metadata
        title = getattr(metadata, "title", None) or url
        return EvidenceSource.create(
            title=title,
            url=url,
            excerpt=result.markdown,
            provider="firecrawl",
        )

Lab 3: Build the Perplexity Research Adapter

Use Sonar to obtain a web-grounded answer and candidate source metadata. Treat the answer as a research aid, not as verified truth; the evidence set remains the contract.

src/scout/providers/perplexity_provider.py
from __future__ import annotations

from dataclasses import dataclass

from perplexity import Perplexity

from scout.models import EvidenceSource


@dataclass(frozen=True)
class GroundedAnswer:
    answer: str
    sources: list[EvidenceSource]


class PerplexityProvider:
    def __init__(self) -> None:
        self.client = Perplexity()

    def research(self, question: str, model: str = "sonar-pro") -> GroundedAnswer:
        completion = self.client.chat.completions.create(
            model=model,
            messages=[
                {
                    "role": "system",
                    "content": "Research conservatively. Separate evidence from inference.",
                },
                {"role": "user", "content": question},
            ],
        )
        answer = completion.choices[0].message.content or ""
        sources = [
            EvidenceSource.create(
                title=item.title or item.url,
                url=item.url,
                excerpt=item.snippet or item.title or item.url,
                provider="perplexity",
            )
            for item in (completion.search_results or [])
        ]
        return GroundedAnswer(answer=answer, sources=sources)
Why not send the Sonar prose directly to Forge?

Because the prose can blend evidence and inference. Forge should receive source objects plus a clearly labelled synthesis, allowing citation checks and later re-evaluation.

Coding exercise

Add source-quality policy

Create a deterministic ranking function that prefers official documentation, standards bodies, peer-reviewed papers, and first-party engineering sources. Never delete lower-ranked sources silently; retain rejection reasons.

Acceptance criteria
  • Ranking does not call an LLM.
  • Domain and source-type rules are configuration, not prompt text.
  • Every rejected source has a machine-readable reason.
  • The final bundle records provider response identifiers when available.

src/scout/nodes.py
from __future__ import annotations

from typing import Literal

from langchain_openai import ChatOpenAI
from langgraph.types import Command, interrupt

from scout.models import ResearchBundle
from scout.planning import QueryPlan
from scout.service import dedupe_sources
from scout.state import ResearchState


class ScoutNodes:
    def __init__(self, perplexity, firecrawl) -> None:
        self.model = ChatOpenAI(model="<approved-model>", temperature=0)
        self.planner = self.model.with_structured_output(QueryPlan)
        self.perplexity = perplexity
        self.firecrawl = firecrawl

    def plan_queries(self, state: ResearchState) -> dict:
        plan = self.planner.invoke(
            f"Topic: {state['topic']}\nReviewer feedback: {state.get('feedback', '')}"
        )
        return {"queries": plan.queries}

    def search(self, state: ResearchState) -> dict:
        found = []
        for query in state["queries"]:
            found.extend(self.perplexity.research(query).sources)
        return {"candidates": dedupe_sources(found)[: state["max_sources"]]}

    def enrich(self, state: ResearchState) -> dict:
        enriched = []
        for source in state["candidates"]:
            try:
                enriched.append(self.firecrawl.scrape(str(source.url)))
            except Exception:
                enriched.append(source)
        return {"candidates": dedupe_sources(enriched)}

    def review(self, state: ResearchState) -> Command[Literal["synthesize", "plan_queries"]]:
        decision = interrupt(
            {
                "question": "Approve this evidence set?",
                "sources": [source.model_dump(mode="json") for source in state["candidates"]],
            }
        )
        if decision.get("approved"):
            return Command(
                update={"approved_sources": state["candidates"], "feedback": ""},
                goto="synthesize",
            )
        return Command(
            update={"feedback": decision.get("feedback", "Find stronger sources")},
            goto="plan_queries",
        )

    def synthesize(self, state: ResearchState) -> dict:
        evidence = "\n\n".join(
            f"[{item.source_id}] {item.title}\n{item.excerpt[:4000]}"
            for item in state["approved_sources"]
        )
        summary = self.model.invoke(
            "Write a concise research brief using only the supplied evidence. "
            "Cite claims with [source_id].\n\n" + evidence
        ).content
        bundle = ResearchBundle(
            topic=state["topic"],
            executive_summary=str(summary),
            sources=state["approved_sources"],
        )
        return {"summary": str(summary), "bundle": bundle.model_dump(mode="json")}
src/scout/graph.py
from __future__ import annotations

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph

from scout.state import ResearchState


def build_scout_graph(nodes):
    builder = StateGraph(ResearchState)
    builder.add_node("plan_queries", nodes.plan_queries)
    builder.add_node("search", nodes.search)
    builder.add_node("enrich", nodes.enrich)
    builder.add_node("review", nodes.review)
    builder.add_node("synthesize", nodes.synthesize)

    builder.add_edge(START, "plan_queries")
    builder.add_edge("plan_queries", "search")
    builder.add_edge("search", "enrich")
    builder.add_edge("enrich", "review")
    # Command-based dynamic routing: ScoutNodes.review returns
    # Command(goto="synthesize") or Command(goto="plan_queries").
    # Do not add a static edge from review; mixing both mechanisms
    # would execute the static and dynamic destinations.
    builder.add_edge("synthesize", END)

    return builder.compile(checkpointer=InMemorySaver())
Command-based dynamic routing: the transition out of review is declared inside ScoutNodes.review() with Command[Literal["synthesize", "plan_queries"]]. LangGraph recommends choosing either static edges or Command routing from a node—not both.

    citation_integrity: int = Field(ge=1, le=5)
    feedback: list[str]

    def passes(self) -> bool:
        return min(
            self.factual_grounding,
            self.structure,
            self.audience_fit,
            self.citation_integrity,
        ) >= 4


model = ChatOpenAI(model="<approved-model>", temperature=0)
evaluator = model.with_structured_output(DraftEvaluation)


def draft(state: WritingState) -> dict:
    prompt = (
        f"Audience: {state['audience']}\n"
        f"Research bundle: {state['research_bundle']}\n"
        "Write a lesson. Every factual claim must cite a supplied source_id."
    )
    return {"draft": str(model.invoke(prompt).content), "revision": 0}


def evaluate(state: WritingState) -> dict:
    hard_failures = deterministic_checks(state["draft"], state["research_bundle"])
    scores = evaluator.invoke(
        f"Evaluate this draft against grounding, structure, audience fit, and citations:\n{state['draft']}"
    )
    feedback = hard_failures + scores.feedback
    return {"feedback": feedback, "approved": not hard_failures and scores.passes()}


def revise(state: WritingState) -> dict:
    revised = model.invoke(
        f"Revise the draft using only the research bundle.\n"
        f"Feedback: {state['feedback']}\nDraft: {state['draft']}\n"
        f"Evidence: {state['research_bundle']}"
    )
    return {"draft": str(revised.content), "revision": state["revision"] + 1}


def deterministic_checks(draft_text: str, bundle: dict) -> list[str]:
    allowed_ids = {source["source_id"] for source in bundle["sources"]}
    used_ids = set(part[1:-1] for part in draft_text.split() if part.startswith("[") and part.endswith("]"))
    failures = []
    if not used_ids:
        failures.append("No citations found")
    if not used_ids.issubset(allowed_ids):
        failures.append("Draft contains unknown citation identifiers")
    return failures

from __future__ import annotations

from langgraph.graph import END, START, StateGraph

from forge.state import WritingState

MAX_REVISIONS = 2


def route_after_evaluation(state: WritingState) -> str:
    if state["approved"]:
        return "publish"
    if state["revision"] >= MAX_REVISIONS:
        return "human_review"
    return "revise"


def publish(state: WritingState) -> dict:
    return {"approved": True}


def human_review(state: WritingState) -> dict:
    return {"approved": False}


def build_forge_graph(nodes):
    builder = StateGraph(WritingState)
    builder.add_node("draft", nodes.draft)
    builder.add_node("evaluate", nodes.evaluate)
    builder.add_node("revise", nodes.revise)
    builder.add_node("publish", publish)
    builder.add_node("human_review", human_review)

    builder.add_edge(START, "draft")
    builder.add_edge("draft", "evaluate")
    builder.add_conditional_edges(
        "evaluate",
        route_after_evaluation,
        {"publish": "publish", "human_review": "human_review", "revise": "revise"},
    )
    builder.add_edge("revise", "evaluate")
    builder.add_edge("publish", END)
    builder.add_edge("human_review", END)
    return builder.compile()

from __future__ import annotations

from dataclasses import dataclass
from time import monotonic


@dataclass
class RunBudget:
    max_tool_calls: int
    max_seconds: float
    started_at: float = 0.0
    tool_calls: int = 0

    def start(self) -> None:
        self.started_at = monotonic()

    def consume_tool_call(self) -> None:
        self.tool_calls += 1
        if self.tool_calls > self.max_tool_calls:
            raise RuntimeError("Tool-call budget exhausted")
        if monotonic() - self.started_at > self.max_seconds:
            raise TimeoutError("Run time budget exhausted")

Every production agentic system is one of these — or a composition

1 · Single agent with tools

User → Agent → Tools → APIs → Results

Use for: Assistants, coding tools, research agents, support bots.
Framework: OpenAI Agents SDK (fastest), LangGraph (most control).

2 · Planner – Executor

User → Planner (capable model) → Task list → Executor (cheap model) → Tools

Use for: Report generation, complex research, structured workflows.
Benefit: Potential cost reduction when a cheaper executor can handle delegated subtasks; validate with workload-specific evals.
Framework: LangGraph (natural fit), CrewAI Hierarchical Process.

3 · Multi-agent collaboration

User → Manager Agent → Specialist Agents → Results

Use for: AI dev teams, content pipelines, complex cross-domain tasks.
Caveat: Coordination overhead hurts performance once a single-agent baseline exceeds ~45% accuracy. Use only when tasks decompose cleanly.

4 · Event-driven

Event (CRM lead, ticket, alert) → Agent → Decision → Action

Use for: Sales automation, DevOps, ops workflows.
Framework: n8n (no-code), LangGraph + Redis/Kafka (code-first), Temporal (durable).

5 · Self-improving (bounded)

Agent → Action → Feedback → Memory update → Agent

Use for: Personal assistants, long-running research, recommendation systems.
Reality check: Most "self-improving" production systems are human-curated refinement loops. Full autonomy remains research-grade.

Three unsolved problems · 2026

These remain the primary barriers to fully autonomous production agents. Recognizing them keeps you honest in interviews.

⚠ Unsolved · 01

Long-term memory

Problem: Agents forget across sessions. Context windows are expensive and degrade with length.

Current best: Hybrid — hot-path context + vector semantic memory + background consolidation.

Gap: Cross-agent memory sharing, provenance tracking, contamination prevention.

⚠ Unsolved · 02

Reliable planning

Problem: Agents lose track of progress, replan poorly on failure, or over-decompose trivial tasks.

Current best: Explicit task graphs (LangGraph), execution monitoring, plan verification via second LLM.

Gap: Hours-long autonomous workflows with reliable replanning.

⚠ Unsolved · 03

Observability at scale

Problem: We can trace everything, but interpreting traces — "why is this agent slowly degrading?" — is largely manual.

Current best: Langfuse / OpenTelemetry traces, LLM-as-judge for sampled grading.

Gap: Automated root-cause analysis for agent failures.

Decision trees

RAG vs fine-tuning

Can prompt / workflow / tool design solve it? → YES: start there. ↓ NO Can retrieval solve a knowledge/freshness gap? → YES: evaluate RAG. ↓ NO Can examples or constrained output solve a behaviour gap? → YES: evaluate that. ↓ NO Consider fine-tuning only with a representative dataset and pre-defined eval criteria.

Workflow vs single agent vs multi-agent

Steps and decisions can be enumerated economically? → YES: deterministic workflow. ↓ NO One bounded agent can resolve runtime uncertainty? → YES: single agent inside deterministic controls. ↓ NO Subtasks need distinct contexts, permissions, ownership, or parallelism? → YES: consider multi-agent/orchestrator-worker. ↓ Independent peer ownership? → consider A2A; otherwise keep internal contracts simpler.

Cloud vs edge

Strict offline/data-residency or device-latency requirement? → evaluate edge/private inference. Hard reasoning quality exceeds the local model? → cloud frontier model or governed fallback. High volume with mixed task difficulty? → evaluate routing/hybrid inference against quality and cost targets.

Build from the bottom up · most teams skip the cheap layers

Most teams skip the cheap layers and go straight to LLM-as-judge, then wonder why evals are noisy and expensive. Build bottom-up.

┌──────────────────┐ │ Human eval │ ← Periodic calibration (quarterly) │ (gold standard)│ └──────────────────┘ ┌──────────────────────┐ │ LLM-as-judge │ ← Every PR / model change │ (RAGAS, G-Eval) │ └──────────────────────┘ ┌──────────────────────────────┐ │ Schema validation │ ← Every commit │ Exact match, code exec │ Fast, cheap, deterministic │ Structural assertions │ └──────────────────────────────┘

Layer 1 · Structural validation (commit-level)

  • JSON schema compliance (Pydantic validators)
  • Tool-call signature verification
  • Regex guards for format compliance
  • Code-execution tests for code-gen agents

Layer 2 · LLM-as-judge (PR-level)

  • RAGAS: faithfulness, answer relevance, context precision / recall
  • DeepEval G-Eval: chain-of-thought reasoning before scoring
⚠ Calibration rule

Calibrate LLM judges against a representative human-labeled sample and track agreement; choose thresholds appropriate to the decision risk.

Layer 3 · Human evaluation (quarterly)

  • Likert ratings on a sampled subset
  • Error-taxonomy tagging (retrieval failure, reasoning error, hallucination, tool misuse)
  • Measure inter-annotator agreement and investigate ambiguous rubric items before automating high-stakes judgments

The three-level agent eval

Evaluate at all three levels or you'll miss critical failure modes.

LevelQuestionMetricsTools
OutcomeDid the task complete successfully?Task success rate, CSAT, deflection rateProduction analytics
TrajectoryWas the path reasonable?Steps to completion, tool selection accuracy, loop detectionLangfuse traces
Per-stepWas each individual action correct?Tool param accuracy, retrieval precision@k, latencyCustom assertions

Anti-patterns to avoid

  • Outcome-only eval: misses agents that get lucky or take inefficient paths
  • Trajectory-only eval: punishes valid creative paths
  • Static eval sets: your data drifts; your eval set should too. Refresh monthly.

Production checklist

Before shipping

  • ☐ Eval harness passes on golden dataset (threshold defined)
  • ☐ Schema validation on 100% of outputs
  • ☐ Cost per task estimated and budgeted
  • ☐ P95 latency measured and within SLA
  • ☐ Human-in-the-loop defined for high-stakes actions
  • ☐ Rollback plan documented (feature flag or model version pin)
  • ☐ PII redaction tested
  • ☐ Prompt-injection red-team suite covers direct prompt injection, indirect prompt injection, malicious tool outputs, and persistent memory/context poisoning
  • ☐ Least-privilege tool scopes, explicit authorisation checks, human approval for consequential actions, untrusted-content boundaries, and deterministic output validation are enforced
Regex is not a security boundary. Signature and keyword filters can catch known strings, but prompt injection has no fool-proof textual detector and can arrive indirectly through webpages, files, tool results, multimodal content, or memory. Use layered controls: treat external content as untrusted data; separate instructions from data; minimise tool permissions; validate tool arguments and outputs in deterministic code; require human confirmation for high-impact actions; sandbox execution; prevent arbitrary exfiltration channels; and continuously red-team the complete agent trajectory.

After shipping

  • ☐ Langfuse / OpenTelemetry tracing live
  • ☐ Cost dashboard tracking $/task and $/user
  • ☐ Canary deployment 1% → 5% → 25% → 100%
  • ☐ Alert on faithfulness degradation > 10% vs baseline
  • ☐ Weekly error-taxonomy review
  • ☐ Monthly eval set refresh

Five questions that separate read-the-docs from shipped-in-prod

Q1

Walk me through naive RAG → advanced RAG → agentic RAG.

Tests RAG depth · retrieval reasoning
+

Strong answer structure

  1. Naive: embed → vector search → stuff into prompt → generate. Fast, simple, fails on complex queries.
  2. Advanced: add hybrid search (BM25 + dense), reranking (cross-encoder), query rewriting. Better recall, still static.
  3. Agentic: agent evaluates sufficiency, reformulates query, iterates retrieval (max N times), then generates with citations. Dynamic, slower, higher quality.
Senior signal: mentions latency trade-offs, cost per query, and when each tier is appropriate.
Q2

Your RAG hallucinates despite good retrieval. Debug it.

Tests systematic thinking
+

Strong answer · ordered

  1. Verify retrieval is actually correct (log chunks, measure recall@k).
  2. Check prompt instructions: "Answer ONLY from context."
  3. Check context positioning (lost-in-the-middle; move best chunks to start/end).
  4. Check chunk granularity (too large dilutes signal; too small fragments facts).
  5. Add faithfulness check (LLM-as-judge or NLI model) before returning the answer.
  6. If all fail, the question likely isn't answerable from the corpus.
Q3

When do you NOT use an agent?

Tests judgment · anti-agent-washing
+

Strong answer

  • Deterministic workflow → use a DAG / state machine.
  • Sub-second latency budget → agent loops add seconds.
  • High cost of failure (finance, medical) without HITL → too risky.
  • Simple RAG or single tool call suffices → don't over-engineer.
  • Single-agent baseline > 45% accuracy and task doesn't decompose cleanly → multi-agent adds overhead without benefit.
Q4

How do you cut LLM costs by 50% without quality regression?

Tests optimization · economics
+

Strong answer · three tiers

  1. Don't call the LLM: semantic + exact caching, trivial query classification to non-LLM paths.
  2. Call a cheaper LLM: model routing classifier; small model handles 70%+, large model fallback.
  3. Make each call cheaper: prompt compression, shorter contexts, output token limits, quantization, batch inference, prompt caching.
Critical

Validate every change against the eval harness. Cost cuts without measurement are just quality cuts in disguise.

Q5

Explain MCP in 60 seconds.

Tests current-state knowledge
+

Strong answer

MCP is an open protocol for connecting AI applications to capabilities such as tools, resources, and prompts. Anthropic donated MCP to the Agentic AI Foundation under the Linux Foundation in December 2025. The 2026-07-28 core specification is stateless and continues to evolve; treat adoption counts as volatile telemetry, not as an architecture justification.

System design scenarios

A

Customer support chatbot · 100k QPS · < 2s latency

High-volume RAG + tool use
+

Architecture

  1. Intent classifier (small model, < 50ms) routes simple FAQs to cached responses.
  2. RAG pipeline (hybrid search + rerank, < 200ms) for complex queries.
  3. LLM (quantized open-weight or API) with constrained JSON output.
  4. Tool layer (order lookup, refund) via MCP with HITL for write operations.
  5. Guardrails: input filtering, output PII redaction, toxicity detection.
  6. Fallback: confidence threshold routes to human with full context.

Key trade-offs

  • Latency vs quality: reranking adds 50–100ms but improves precision 15–25%.
  • Cost vs coverage: open-weight model for 80% traffic, API for edge cases.
B

Real-time fraud detection · < 50ms

Why an LLM is the wrong tool
+

Architecture

  1. Feature pipeline: Kafka → Flink for real-time aggregations.
  2. Model: XGBoost or LightGBM — not an LLM. Deterministic, fast, explainable.
  3. Inference: ONNX Runtime, co-located with feature store.
  4. Decision: score → policy engine (allow / step-up / block).
  5. Explainability: SHAP values surfaced to analysts.
Why not an LLM? Latency budget and deterministic requirements. Use the right tool for the job.

Protocol

The current MCP core is stateless and the July release adds multi-round-trip requests, header-based routing, cacheable list results, authorization hardening and an extensions framework. Interoperability

A2A 1.0

A2A defines interoperability between independent agents. Agent Cards have defined required/optional fields and can carry signed metadata; rate-limit policy is operational guidance rather than a required Agent Card field.

User interface

AG-UI, A2UI and MCP Apps are different layers

AG-UI is an Agent↔User Interaction event protocol. A2UI is a generative-UI specification. MCP Apps is an MCP extension for interactive UI returned by tools. Do not collapse them into one protocol.

Framework

PydanticAI expanded beyond a “simple loop” role

Current documentation covers typed tools/outputs, graphs, AG-UI, MCP and first-party durable-execution integrations including Temporal. Use it where those abstractions fit; do not force a framework migration solely because a workflow becomes durable.

Lesson 00B: How an LLM Actually Runs

Move beyond “probabilistic autocomplete.” An inference request becomes token IDs, tensor operations through transformer blocks, logits over the vocabulary, token selection, and then another pass. The two performance regimes—prefill and decode—behave differently and drive many production decisions.

Core mental model

An LLM is a very large numerical program. Text is the interface; tensor operations are the work.

1 · InputText → tokensTokenizer maps strings to integer IDs.
2 · RepresentationEmbeddingsToken IDs become dense vectors.
3 · TransformerAttention + MLPRepeated blocks transform the hidden state.
4 · PredictionLogitsScores are produced for the next token.
5 · SamplingChoose tokenGreedy, temperature, top-p, etc.
6 · LoopDecode againRepeat until stop condition.

What to understand

  • Attention mixes information across positions; the MLP/FFN performs large per-token transformations.
  • Prefill processes the prompt in parallel; decode generates token-by-token and is usually more memory-bandwidth sensitive.
  • KV cache stores reusable attention keys/values so previous tokens are not fully recomputed on every decode step.
  • Model architecture choices such as GQA/MQA, MoE, context length and vocabulary size affect runtime cost.

Engineering decisions

  • Separate time-to-first-token (TTFT) from time-per-output-token (TPOT).
  • Do not compare models on parameter count alone; consider architecture, precision, context and serving engine.
  • Understand whether your workload is prompt-heavy, generation-heavy, latency-sensitive or throughput-oriented.

Lesson 00C: GPU Fundamentals for AI Engineers

GPUs matter because neural networks contain enormous amounts of parallel linear algebra. You do not need to become a chip designer, but you should understand the hardware constraints that determine whether a model fits, how quickly it runs, and how well it serves concurrent users.

Core mental model

CPU = a smaller number of sophisticated general-purpose workers. GPU = a massive parallel throughput machine built to perform the same kinds of numerical operations across many data elements.

Vocabulary that matters

  • VRAM capacity: whether model weights + KV cache + runtime workspace fit.
  • Memory bandwidth: how quickly weights/activations can move; decode performance can become bandwidth-bound.
  • Compute throughput: FLOPS/TOPS at FP32, TF32, BF16/FP16, FP8, INT8, etc.
  • SMs / compute units: hardware blocks scheduling groups of GPU threads.
  • Tensor Cores: specialised matrix-multiply hardware used heavily by modern deep learning.
  • Interconnect: PCIe/NVLink/networking becomes critical once one GPU is not enough.

Architectural judgement

  • A GPU with more VRAM can be more useful than a nominally faster GPU when the model otherwise spills or cannot load.
  • Peak FLOPS is not application performance. Kernel efficiency, precision, batching and memory traffic matter.
  • CPU-only inference can be valid for smaller quantised models and low-throughput workloads; “GPU required” is workload-dependent.

Lesson 00E: Memory, Precision & Quantization

“Will this model fit?” should be answerable with a rough calculation before you download anything. Weight memory is only the first term; inference also needs KV cache and runtime workspace, while training adds gradients, optimiser states and activations.

First-order inference estimate
weight memory ≈ parameter count × bytes per parameter
Example: 8B parameters × 2 bytes (FP16/BF16) ≈ 16 GB just for weights, before cache/workspace overhead. Quantisation changes the storage term but introduces format/kernel trade-offs.

Precision map

  • FP32: 4 bytes/parameter; rarely necessary for routine LLM inference.
  • FP16/BF16: 2 bytes; common training/inference formats, with BF16 offering a wider exponent range.
  • FP8: lower memory/bandwidth with hardware/software support and calibration/scaling considerations.
  • INT8 / INT4 / 4-bit formats: major memory reduction for inference; quality and kernel support vary.

Memory consumers

  • Weights
  • KV cache — grows with sequences/concurrency
  • Activations / temporary tensors
  • CUDA graphs and runtime workspace
  • Training: gradients + optimiser states + saved activations

Lesson 00F: LLM Inference & Serving

Running one prompt in a notebook and serving hundreds of concurrent requests are different engineering problems. Serving engines exist to schedule requests, manage KV-cache memory, batch work and select high-performance kernels.

Production metrics

  • TTFT: time until the user sees the first generated token.
  • TPOT / inter-token latency: responsiveness while streaming.
  • Throughput: tokens/second or requests/second across the server.
  • Goodput: useful requests meeting your latency SLO, not raw benchmark throughput.

  • Chunked prefill: schedule long prompts more fairly.
  • Speculative decoding: draft tokens cheaply and verify with the target model.
  • Tensor/pipeline/expert parallelism: distribute models that exceed one device or need more throughput.

Lesson 00G: Training & Fine-Tuning Compute

Inference answers “how do I run this model?” Training adds the backward pass, gradients and optimiser state. This is why training memory and compute can be several times the weight footprint, and why parameter-efficient fine-tuning matters.

Training loop

  1. Forward pass → predictions and loss.
  2. Backward pass → gradients.
  3. Optimiser step → update parameters.
  4. Repeat over batches; validate and checkpoint.

Memory controls

  • Mixed precision
  • Gradient accumulation
  • Gradient checkpointing
  • Activation offload
  • Sharded states (FSDP / ZeRO)

Fine-tuning judgement

  • Prompt/RAG first when knowledge freshness or grounding is the problem.
  • LoRA/QLoRA when you need behavioural/style/task adaptation without updating every base parameter.
  • Full fine-tuning only when evidence justifies the cost and data requirements.
  • Evaluate against a frozen baseline; fine-tuning can regress capabilities outside the target domain.

Containerisation packages the server consistently, but security also depends on non-root users, minimal images, secrets outside the image, health endpoints, resource limits, and a defined outbound network policy.

Core mental model

Identity enters at the edge; authorisation follows every resource; the container limits the process—not the business permission model.

→
03Resolve tenant/scopes
→
04Authorise tool/resource
→
05Run in container
→
06Audit

Engineering decisions

  • Use OAuth 2.1-compatible flows for remote interactive clients.
  • Enforce tenant filters inside repositories, not prompts.
  • Build immutable images and inject configuration at runtime.

Practical exercise

Create a permission matrix for researcher, editor, approver, and administrator across Scout and Forge tools.

Does Docker provide multi-tenant security by itself?

No. Containers isolate processes; application-level identity, tenant scoping, authorisation, data isolation, and auditing are still required.

Lesson 33: Preparing For Deployment: Database and File Download/Upload

Production agents need durable state beyond chat history. Use a relational database for runs, state transitions, permissions, manifests, and references; object storage for source files and generated artifacts; and a vector index for retrieval representations. Files need size/type limits, malware scanning where appropriate, checksums, tenant paths, signed access, retention, and deletion.

Core mental model

Store metadata and truth in transactions; store large blobs in object storage; store embeddings as derived indexes that can be rebuilt.

01Authorise upload
→
02Validate/scan
→
03Stream to object store
→
04Write metadata transaction
→
05Process asynchronously
→
06Publish signed download

Engineering decisions

  • Use immutable artifact versions.
  • Commit state transitions and outbox events atomically.
  • Treat vector indexes as replaceable projections.

Practical exercise

Design tables for run, artifact, source, evidence, approval, event, and eval result. Define which data lives in object storage and which is a derived index.

Failure modes to recognise
  • Large files loaded fully into web-process memory.
  • Database rows pointing to objects that failed to upload.
  • Deleting metadata but retaining private blobs or embeddings.
Memory BankTransactions own truth; objects own bytes; indexes own speed.
Knowledge Check

Why should embeddings be treated as derived data?

They depend on chunking and model versions and should be rebuildable from authoritative source artifacts and metadata.

Lesson 34: Continuous Deployment for AI Engineering

Continuous deployment promotes a tested artifact through environments with versioned configuration, database migrations, smoke tests, health checks, traffic control, monitoring, and rollback. AI changes include model aliases, prompt versions, tool schemas, retrieval indexes, and eval thresholds; these should be deployable and reversible independently where practical.

Core mental model

A release is a bundle of code, configuration, models, prompts, schemas, data projections, and evidence. Deploy it as a versioned system, not a container alone.

01Build immutable image
→
02Verify provenance
→
03Deploy revision
→
04Migrate safely
→
05Smoke/eval
→
06Shift traffic
→
07Observe
→
08Rollback or promote

Engineering decisions

  • Use canary or traffic-splitting for material behaviour changes.
  • Separate expand and contract database migrations.
  • Define rollback for prompt/model/config changes as well as code.

Practical exercise

Write a release manifest containing image digest, commit, config version, prompt versions, model aliases, schema versions, migration, eval run, and rollback target.

Failure modes to recognise
  • Latest tags and mutable model names with no manifest.
  • Auto-scaling without concurrency and provider-rate-limit planning.
  • Rollback that restores code but not schema or prompt compatibility.
Memory BankDeploy revisions, shift traffic, watch outcomes, preserve a reversible path.
Knowledge Check

What should trigger automatic rollback?

Predefined hard signals such as elevated error rates, security/policy violations, incompatible schemas, health failures, or severe task-success regression—not subjective one-off outputs.

G

Glossary

Compact definitions for retrieval practice and design reviews.

Agent

A model-driven loop that dynamically chooses actions or tool use to achieve a goal.

Workflow

A system whose execution paths are primarily defined in code.

Harness

The model, prompts, tools, middleware, context strategy, runtime, and controls surrounding an agent loop.

Orchestrator-worker

A pattern where an orchestrator dynamically decomposes work and delegates subtasks to workers.

Evaluator-optimizer

A bounded loop where an evaluator critiques an output against criteria and an optimizer revises it.

Context engineering

Selecting, structuring, and maintaining the information presented to a model at inference time.

Structured output

Model output constrained to a typed schema for validation and downstream use.

Tool

A typed external capability the model can request, such as search, calculation, or an API action.

MCP

An open protocol for connecting AI applications to tools, resources, and prompts through clients and servers.

RAG

Retrieval-augmented generation: retrieving external evidence and providing it to a generator.

Agentic RAG

RAG in which a model can choose or iterate retrieval strategies rather than using one fixed query path.

CAG

Cache-augmented generation: preloading stable knowledge into model context or cached prefixes instead of runtime retrieval.

Working memory

The current task state and context available during inference.

Episodic memory

Stored records of prior interactions, events, or completed runs.

Semantic memory

Durable facts and concepts stored independently of a particular episode.

Human-in-the-loop

A system design where humans inspect, decide, correct, or approve at explicit checkpoints.

Trace

A causal record of one request across nested workflow, model, retrieval, and tool operations.

Span

A timed unit of work within a trace.

Golden set

A curated evaluation dataset with reviewed inputs, expected behaviour, and grading criteria.

LLM-as-a-judge

A model used to evaluate outputs against a rubric, ideally calibrated against expert labels.

Idempotency

The property that repeating an operation with the same key does not create unintended duplicate effects.

Provenance

The origin, version, transformations, and lineage of data or evidence.

Compaction

Summarising and externalising long context while preserving the state needed to continue work.

Blast radius

The maximum harm a failure or compromised capability can cause.
