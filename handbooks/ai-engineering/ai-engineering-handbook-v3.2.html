01

LLM Mechanics & Tool Use

Foundation · The atomic loop
+

Pareto Focus

  • Tokens are the operating unit: tokenization affects limits, truncation, latency, and cost; generation is sequential, so long outputs are usually slower than equally sized inputs.
  • Sampling is not truth control: temperature and related parameters change the output distribution. Use schemas, validators, evidence, and task-specific evals for reliability.
  • The atomic loop: User → LLM → JSON → Tool → Result → LLM → Answer. Every agentic system is this loop, repeated.
  • Structured output: Schema-constrained output where supported, plus Pydantic validation, helps enforce interface shape. Handle refusals, truncation and retries, and validate facts and business rules separately; valid JSON is not proof of correctness.
🧠 Explain it back

Explain tool calling to a non-engineer. Who actually runs the tool?

Say or write your answer first, then compare.

Compare with a model answer

An LLM predicts the next piece of text. With tool calling it can answer with a structured request (a JSON function call) instead of prose. The model never runs the tool: your code checks the request, runs it and feeds the result back. The useful behaviour comes from that loop, not from the model alone.

Build: Atomic Agent

A 100-line Python script that takes a user query, decides between three tools (web search, calculator, weather), executes the chosen tool, returns structured JSON.

Success criteria: Handles 10 diverse queries without schema violations.

Prompt & Context Engineering

Foundation · Prompts are code
+

Pareto Focus

  • Six-block template: Role → Context → Task → Format → Rules → Examples. Use it as a starting structure, then test which blocks materially improve the task.
  • Reasoning support: Ask for explicit plans, checks, evidence, or intermediate artifacts when the task needs them; evaluate the final result rather than assuming visible reasoning guarantees correctness.
  • Context = RAM: What you put in (retrieved docs, memory, tool schemas) matters more than how you phrase the question.
🧠 Explain it back

Why should a prompt change go through the same process as a code change?

Say or write your answer first, then compare.

Compare with a model answer

Prompts are code, not prose. We version them, test them, deploy them through CI/CD. A prompt change is a code change.

Build: Prompt Versioning System

Git-tracked prompt registry. Jinja2 or YAML templates separate from code. A/B test two variants against a 20-example eval set. Measure correctness, latency, token cost.

03

RAG Foundations

Retrieval · Runtime knowledge injection
+

Pareto Focus

  • Chunking: A 512-token chunk with modest overlap is a baseline experiment, not a default. Iterate using retrieval and end-task evaluation.
  • Grounding is a routing decision: stable rules may fit the prompt; live records belong behind tools or APIs; unstructured knowledge may require search. Do not put every source into a vector index.
  • Retrieval choice follows query shape: compare relational queries, keyword search, dense retrieval, hybrid retrieval, and graph traversal on the actual access patterns.
  • Freshness and authority: ingestion needs ownership, update cadence, access control, lineage, and deletion behavior. Relevant stale data is still wrong.
🧠 Explain it back

When is a vector database the wrong way to ground an answer?

Say or write your answer first, then compare.

Compare with a model answer

Grounding gives the model the right evidence at decision time. Sometimes that means search; sometimes it means querying the source system. A vector database is one route, not the definition.

Agentic RAG & Memory

Retrieval · Self-evaluating loops
+

Pareto Focus

  • Agentic loop: Retrieve → Evaluate sufficiency → Reformulate → Re-retrieve (max 3 iterations) → Generate. The agent decides when it knows enough.
  • Three memory tiers: Short-term (conversation), Semantic (user facts in vector DB), Episodic (past decisions as few-shot). Procedural is nice-to-have.
  • Query reformulation: HyDE (Hypothetical Document Embeddings) and step-back prompting are two techniques worth testing. Keep whichever improves retrieval recall on your own question set, and drop the rest.
🧠 Explain it back

What does agentic RAG do that a single retrieval pass cannot, and what does it cost you?

Say or write your answer first, then compare.

Compare with a model answer

Single-pass RAG retrieves once and answers with whatever came back. Agentic RAG checks whether the evidence is enough and, if not, searches again with a better query, like a researcher checking sources before writing. The price is extra latency, tokens and loop logic, so cap the iterations and measure whether the extra rounds improve answers.

Build: Self-Evaluating Research Agent

Extend Week 3. Add sufficiency-evaluator node, query reformulation, semantic memory in pgvector. Evaluate on a 30-question test set measuring retrieval recall, faithfulness, latency.

LangGraph Deep Dive

Agent core · State machines over chat loops
+
📌 Status · checked 13 October 2026

LangGraph 1.2.14 was the current PyPI release on 13 October 2026 (released 6 October). Its maintainers describe it as a low-level orchestration framework for long-running, stateful agents, with production users including Klarna, Replit, and Elastic. Treat it as one mature option, not a universal default: select it when explicit state, durable execution, and controlled orchestration fit the workload.

Pareto Focus

  • State machines, not chat loops: Explicit nodes (functions) and edges (transitions) make agents debuggable.
  • Checkpointing: Persistence turns a script into a product. Users can resume, rewind, inspect.
  • Human-in-the-loop: interrupt nodes for approval. Non-negotiable for any agent with write access.
🧠 Explain it back

Why draw the state machine before writing agent code?

Say or write your answer first, then compare.

Compare with a model answer

Drawing the states and transitions first makes you decide where the agent can stop, wait for approval, retry or resume. If you cannot draw it, you cannot test it, and the behaviour will only be discovered in production.

Build: Approval-Required Agent

Plans a multi-step task (research → write → send). Pauses at "send" for human approval via a simple web UI. Resumes or aborts based on input. Persists state to PostgreSQL. Success criteria: kill the process mid-task, restart, it resumes correctly.

MCP & the Tool Ecosystem

Agent core · USB-C for AI
+
📌 Status · checked 13 October 2026

MCP is governed through the Linux Foundation's Agentic AI Foundation. Anthropic's December 2025 donation announcement reported 10,000+ active public servers and 97M+ monthly Python and TypeScript SDK downloads; treat those as dated adoption figures, not live counters. 2026-07-28 remains the current specification (checked 13 October 2026). MCP is a widely adopted open standard for connecting AI applications to tools and context.

Pareto Focus

  • MCP is USB-C for AI: One standard for tools. Learn once, use everywhere.
  • Build > consume: Building one MCP server teaches you more than consuming ten.
  • Schema-first design: Typed tool interfaces make agent-tool integration failures easier to detect, test, and contain.
🧠 Explain it back

What problem does MCP solve, and what does it leave to you?

Say or write your answer first, then compare.

Compare with a model answer

MCP is a contract between an AI application and a tool server. The server describes its tools, resources and prompts; the client inside the host application discovers and calls them, so any compatible host can reuse the same server instead of a bespoke integration. MCP does not decide who may call a tool or whether a call is safe: authorisation, approval and validation stay with you.

Build: MCP Server + Client

An MCP server exposing a SQLite database (product catalog). Connect to your LangGraph agent from Week 5. Connect the same server to Claude Desktop. Document the schema with OpenAPI-style descriptions.

Evaluation & Observability

Production · Eval-driven development
+

Pareto Focus

  • EDD: Define your eval set before your agent. If you can't measure it, you can't ship it.
  • Three-level eval: Outcome (did it finish?), Trajectory (was the path reasonable?), Per-step (was each tool call correct?).
  • Langfuse: Self-hostable, OpenTelemetry-native, LangGraph-aware. The pragmatic choice for solo developers and small teams.
🧠 Explain it back

Why define the evaluation set before building the agent?

Say or write your answer first, then compare.

Compare with a model answer

Anyone can make a demo work once. An evaluation set shows how often it works, where it fails and whether a change made things better or worse. Defining it first stops you from tuning the system to the examples you happened to try.

Build: Eval Harness

Build at least 30 representative cases with human labels, important risk slices, and deterministic assertions where possible. Add an LLM judge only after measuring agreement and disagreements against those labels. Trace every node. Derive release thresholds from failure cost and block regressions by slice—not from a generic percentage.

Safety, Guardrails & Cost Control

Production · Defense in depth
+

Pareto Focus

  • Defense in depth: Input validation → Output guardrails → Budget limits → Audit logs. No single layer suffices.
  • Cost is a feature: Eval-qualified routing can reduce cost by using expensive models only where they improve accepted-task outcomes.
  • Prompt injection: untrusted text can steer the model. Unlike SQL injection, there is no complete fix such as parameterised queries, so design for containment: privilege separation, tool allow-lists, deterministic authorisation and approval for consequential actions. Prompt wording alone is not a control.
🧠 Explain it back

Why can't a better system prompt make an agent safe?

Say or write your answer first, then compare.

Compare with a model answer

Safety isn't a bolt-on; it's architecture. You don't secure a bank by hiring better tellers; you secure it with vaults, cameras, and alarms.

Add to Week 6 agent: input regex guard, output PII redaction, token budget per session (10K in / 2K out), cost dashboard, audit log of every tool call and approval.

Multi-Agent & Capstone Design

Integration · When (not) to multiply agents
+

Pareto Focus

  • Multi-agent is a scaling tool, not a default. Compare against a strong single-agent baseline and use multiple agents only when decomposition or independent review creates measured value.
  • Supervisor pattern: One coordinator, specialist workers. Usually the simplest multi-agent pattern to trace and debug.
  • Plan-and-execute: A capable model plans and a lower-cost model executes when task decomposition permits it. Compare accepted-result quality, coordination overhead, latency and total token cost with a single-model baseline.
🧠 Explain it back

When are multiple agents worth their cost?

Say or write your answer first, then compare.

Compare with a model answer

Multi-agent is hiring a team. If one person can do the job well, more people creates meetings, miscommunication, delay. Only go multi-agent when the work genuinely requires different expertise.

Engineering practice.

Shape the right problem · direct coding agents · prove the result

Connect the dots: compare decision mechanisms

For a bounded judgement, compare rules, a conventional classifier, a typed decision model such as Jev or Laya, and a generative baseline. Start with the canonical selection guide; this exercise owns the comparison work.

  1. Create synthetic support tickets with fixed labels, an unknown path and explicit urgency criteria. Separate development and held-out cases before tuning.
  2. Run the same cases through your available candidates. Keep inputs and labels consistent; record unavailable candidates as not evaluated. Mocked responses test wiring only.
  3. Measure per-class errors, accepted-case coverage, abstention, p95 latency and full cost per successful task. Investigate missing evidence, a new language and an ambiguous label pair.
  4. Choose thresholds on development data using decision-model acceptance. State when rules or a cheaper baseline win.
  5. Write an ADR, save the evaluation packet, then continue to the agent integration exercise.

Feynman check: Why can an allowed answer still be wrong? What would make you remove the router? Product examples and sources are maintained in the canonical selection guide.

The shift

Code generation is becoming cheaper. Intent, architecture, verification, and accountability are not. Treat the coding agent as an execution system whose work must stay inside explicit scope and evidence gates.

The AI engineering work loop

This is a loop, not a waterfall. A failed verification may expose a bad implementation, but it may also reveal a bad requirement, weak data, an invalid evaluator, or a problem that never needed AI. Move back to the earliest incorrect assumption.

Coding-agent engineering

Using a coding agent well is not the same as building an agentic product. The engineering skill is directing uncertain execution while preserving human ownership of intent, risk, and acceptance.

Context is an engineered dependency

  • Standing context: keep repository conventions, architectural boundaries, commands, and data-access rules in a short maintained file.
  • Task context: supply the goal, non-goals, exact evidence, affected interfaces, and acceptance tests; do not dump the whole repository.
  • Decision continuity: record changed assumptions and review rulings in durable artifacts rather than relying on chat history.
  • Parallel work: split only independent files or components, assign explicit ownership, and integrate through one review point.
  • Context debt: remove obsolete instructions, duplicated plans, abandoned helpers, and generated clutter during retrospectives.

Shaping the build

An engineer does not earn an AI solution merely by finding a model that can attempt it. Shape the smallest intervention that improves a real outcome.

1 · Problem — Whose decision or workflow is failing, and what evidence proves it? 2 · Outcome — What measurable behavior should improve, by how much, and by when? 3 · Baseline — What do rules, search, forms, process change, or ordinary software achieve first? 4 · AI fit — Does uncertainty or unstructured input justify a probabilistic component? 5 · Failure budget — Which errors are tolerable, reviewable, or forbidden? 6 · Smallest test — What MVP can reach real users without crossing the production trust boundary? 7 · Learn — What did users, traces, costs, and error slices teach us to change next?
Prefer ordinary software when
  • Rules are stable and complete.
  • The correct result must be deterministic.
  • Latency or failure cost leaves no room for model uncertainty.
  • A form, query, search index, or workflow change solves the user problem.
Consider AI when
  • Inputs are ambiguous, unstructured, or multimodal.
  • Useful quality can be measured on representative cases.
  • Failures can be detected, contained, reviewed, or reversed.
  • The expected user value exceeds inference, evaluation, and operating cost.

Worked framing: support-ticket triage

Problem: specialists spend time re-routing ambiguous tickets. Baseline: measure rules plus form improvements before adding a model. AI fit: classify only the unstructured remainder and attach confidence plus evidence. Failure budget: a wrong suggested queue is reviewable; an autonomous refund is forbidden. Smallest test: run in shadow mode on representative historical tickets, then compare routing accuracy, handling time, abstention, cost, and performance across customer segments.

Three unsolved problems · 2026

These remain the primary barriers to fully autonomous production agents. Recognizing them keeps you honest in interviews.

⚠ Unsolved · 01

Long-term memory

Problem: Agents forget across sessions. Context windows are expensive and degrade with length.

Practical baseline: Hybrid — hot-path context + vector semantic memory + background consolidation.

Gap: Cross-agent memory sharing, provenance tracking, contamination prevention.

⚠ Unsolved · 02

Reliable planning

Problem: Agents lose track of progress, replan poorly on failure, or over-decompose trivial tasks.

Practical baseline: Explicit task graphs (LangGraph), execution monitoring, plan verification via a second model.

Gap: Hours-long autonomous workflows with reliable replanning.

Observability at scale

Decision trees

Choose the intervention layer

Requirement or evaluator is wrong? → Repair the definition of success. Evidence is missing, stale, or unauthorized? → Repair data and access. Code, query, search, or tool can solve it deterministically? → Prefer that baseline. The model received the wrong context? → Fix prompt, API/SQL access, retrieval, or examples. The workflow or control boundary failed? → Fix state, interface, authorization, or verification. A stable model-capability gap remains? → Evaluate routing or adaptation with rollback gates.

Single agent vs Multi-agent

Task is deterministic with clear steps? → Workflow (LangGraph DAG) ↓ Task needs reasoning + 2–5 tool calls? → Single Agent (ReAct) ↓ Task decomposes into distinct expertise domains? → Multi-Agent (Supervisor) ↓ Task requires debate / consensus? → Peer-to-Peer (research only)

Cloud vs Edge deployment

Very tight end-to-end latency (for example under 200 ms)? → Measure first; a small model close to the user (on-device, edge or nearby region) or a non-generative path may be needed Data cannot leave premises? → Edge or private cloud Complex reasoning required? → Cloud (frontier LLM) High volume, cost-sensitive? → Hybrid (SLM edge + LLM cloud fallback)

Evaluation and error analysis.

Find the first failure · fix the cheapest layer · gate the release

Most teams skip the cheap layers and go straight to LLM-as-judge, then wonder why evals are noisy and expensive. Build bottom-up—but do not stop at a score. Evaluation-driven development is a decision loop for choosing the next intervention.

The error-analysis loop

Start with the first independent failure, not every downstream symptom. Review both aggregate performance and slices such as intent, language, customer segment, document type, tool, risk class, or workflow length. Averages can improve while an important cohort regresses.

Observed failureInspect firstLeast-invasive intervention
Relevant evidence never reached the modelIngestion, permissions, query, retrieval recall, freshnessRepair data or retrieval before changing the model
Evidence was present but ignored or misusedPrompt contract, context order, ambiguity, reasoning budgetClarify instructions, restructure context, add a check
Tool call was invalid or unsafeTool description, schema, authorization, validation, stateTighten interface and policy; add deterministic verification
Workflow looped, stopped early, or duplicated workState transitions, stop conditions, retry ownership, idempotencyFix orchestration before adding agents or a larger model
Quality varies by stable, repeated task sliceExamples, evaluator labels, model capability, latency/cost budgetRoute or adapt only after harness and data fixes are exhausted
Metric improves but users reject the resultEvaluator rubric, sampling, hidden product requirementRepair the evaluator or reshape the requirement
Evaluate the evaluator

For every consequential automated judge, maintain representative human-labelled examples, disagreement cases, slice-level agreement, and a review trigger. An evaluator is another fallible model of success—not ground truth.

Build checks from the bottom up

Run cheap deterministic checks on every commit: schema validation, exact match, code execution and tool-signature checks. Add a calibrated LLM judge (for example a RAGAS faithfulness score or a G-Eval rubric) on every pull request or model change. Keep human review continuous for high-risk changes and sampled for stable, lower-risk behaviour, and tag what reviewers find with an error taxonomy. When you report human agreement, give the statistic, sample size and class balance; no single κ cut-off proves label quality. The AI Evaluation Field Guide covers graders, judge calibration and statistics in depth.

The three-level agent eval

Evaluate at all three levels or you'll miss critical failure modes.

LevelQuestionMetricsTools
OutcomeDid the task complete successfully?Task success rate, CSAT, deflection rateProduction analytics
TrajectoryWas the path reasonable?Steps to completion, tool selection accuracy, loop detectionLangfuse traces
Per-stepWas each individual action correct?Tool param accuracy, retrieval precision@k, latencyCustom assertions

Anti-patterns to avoid

  • Outcome-only eval: misses agents that get lucky or take inefficient paths
  • Trajectory-only eval: punishes valid creative paths
  • Static eval sets: your data drifts; your eval set should too. Refresh monthly.

Production checklist

Before shipping

  • ☐ Eval harness passes on golden dataset (threshold defined)
  • ☐ Schema validation on 100% of outputs
  • ☐ Cost per task estimated and budgeted
  • ☐ P95 latency measured and within SLA
  • ☐ Human-in-the-loop defined for high-stakes actions
  • ☐ Rollback plan documented (feature flag or model version pin)
  • ☐ PII redaction tested
  • ☐ Adversarial prompt and tool-content cases tested; instruction/data separation, least-privilege tools, deterministic authorization, sandboxing, and approval gates enforced — see Production AI Assurance

After shipping

  • ☐ Langfuse / OpenTelemetry tracing live
  • ☐ Cost dashboard tracking $/task and $/user
  • ☐ Canary deployment 1% → 5% → 25% → 100%
  • ☐ Alert on faithfulness degradation > 10% vs baseline
  • ☐ Weekly error-taxonomy review
  • ☐ Monthly eval set refresh

Cost estimation

Monthly cost = input tokens × input price + output tokens × output price. Change the inputs to match your workload; the defaults are the worked example.

Optimisation levers

  • Cache stable repeated prefixes.
  • Route only eval-qualified tasks to cheaper models.
  • Reduce unnecessary context without discarding evidence.
  • Batch asynchronous workloads when the provider supports it.

Recalculate with current provider pricing and measured workload data. Do not copy a generic savings percentage.

What changed since the original notes · what to track

⚡ The headline shifts
  • Claude's active lineup changed. Anthropic now lists Fable 5.1, Opus 5.5, Sonnet 5.5, and Haiku 5.5. Select by eval results and workload economics rather than treating one model as a permanent default.
  • MCP matured. It remains under the Linux Foundation's Agentic AI Foundation; the current specification, checked 13 October 2026, is 2026-07-28 and includes optional extensions for tasks, skills, and MCP Apps.
  • LangGraph stayed on the 1.2 line. PyPI listed 1.2.14, released 6 October 2026. It is a mature low-level option for explicit, long-running stateful orchestration—not an automatic choice for every agent.
  • The EU AI Omnibus entered into force on 27 July 2026. Annex III high-risk rules now apply from 2 December 2027; Annex I product-embedded high-risk rules apply from 2 August 2028.
  • Agent protocols are separating concerns. MCP covers tools and context, A2A covers agent interoperability, and AG-UI covers agent-to-frontend events. Treat each implementation as a maturity and security decision.
  • Microsoft Agent Framework 1.0 is production-ready. Microsoft directs inherited AutoGen and Semantic Kernel users to its migration guidance; new projects should compare it with LangGraph and other runtimes against explicit requirements.

  1. Verify current model IDs and pricing against the official Anthropic / OpenAI / Google docs.
  2. Check LangGraph version (PyPI) and re-pin dependencies.
  3. Re-read the latest MCP spec changelog at modelcontextprotocol.io.
