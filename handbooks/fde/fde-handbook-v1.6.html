Forward Deployed AI Engineering

From ambiguous enterprise problem to measurable production outcome.

This handbook treats FDE as a craft, not a job title. The core skill is the ability to enter a messy customer environment, discover the real constraint, build and deploy the smallest useful system, prove it passes the value, quality, safety, operability, economics and adoption gates, then codify the pattern so the next deployment is faster.

An FDE owns the uncomfortable middle between “the model/platform can do this” and “the customer runs this reliably in production.”

Apply the architect lens to the existing capstone

Model answer (open after you have tried)

A design rests on assumptions about your systems, data and people, and many of them are only tested when real code meets real systems. Explain to a sponsor which skills on the engagement team matter most for their project, and why coding alone is not enough.

Model answer (open after you have tried)

Two things decide whether a project succeeds. First, solving the right problem: understanding how the work is done today, who owns the result and what change would be worth paying for. 4. Transition roadmap ↑ top

This roadmap assumes an experienced enterprise professional moving toward hands-on applied AI. It deliberately avoids a “learn every framework” trap.

If you are coming from delivery, product or enterprise architecture rather than software engineering: do not spend the first phase collecting more discovery or stakeholder frameworks. Keep those strengths, but bias your first investment toward hands-on engineering: Python services, tests, APIs, persistence, debugging, containers and one deployed AI workflow. Your goal is to become the person who can carry a customer problem through implementation, not merely frame it well.

Phase A — Engineering credibility

  • Build and test a Python API service with typed models, persistence and external integrations.
  • Be comfortable reading TypeScript and shipping a small full-stack feature.
  • Debug a failing service using logs/traces rather than trial-and-error prompting.
  • Explain idempotency, retries, timeouts, queues, transactions and concurrency from examples.

Phase B — Production AI credibility

  • Build a model-agnostic LLM service with structured output, tool calls and fallback.
  • Create an eval dataset before optimising prompts.
  • Add RAG only where retrieval is actually required; measure retrieval separately from generation.
  • Instrument latency, cost, failure categories and tool execution.
  • Implement an approval boundary for consequential side effects.
  • Persist long-running task state; implement cancellation, re-entry and idempotent resume.
  • Enforce user/workload identity and tool permissions outside the model.

Phase C — Forward-deployed credibility

  • Run discovery from an intentionally ambiguous brief.
  • Write a one-page engagement framing: current state, target outcome, MVP, assumptions, risks and metrics.
  • Ship a production-like deployment with runbook and operational dashboard.
  • Demonstrate a failure, recovery and post-incident improvement.
  • Produce a reusable pattern/playbook from the engagement.

Phase D — Interview and market readiness

  • Two strong deployment case studies.
  • One agent/eval-heavy case study.
  • One brownfield enterprise integration case study.
  • System-design interview practice plus coding fluency.
  • Customer discovery / ambiguity case drills.

Assignment 5A — “Unreliable upstream”

2–4 hours

Build a resilient integration service

Create a small API that calls a deliberately unreliable upstream dependency.

  • Implement timeout, bounded retry with backoff, circuit-breaking or fail-fast policy, idempotent request handling and typed errors.
  • Add unit tests for transient failure, permanent failure, timeout and duplicated request.
  • Expose trace/correlation IDs in logs.

Pass condition: you can explain exactly which failures are retried, which are not, and what the caller sees.

6. System design for FDEs ↑ top

FDE system design is usually brownfield: existing identity, databases, message buses, approvals, regulations and operational expectations already exist. “Start from a blank whiteboard” is the exception.

Questions to ask before drawing boxes

  1. What is the authoritative system of record?
  2. Which action is reversible? Which is not?
  3. What can safely happen twice?
  4. What happens after a process crashes halfway through?
  5. Where is identity established and authorization enforced?
  6. What data may cross the model boundary?
  7. Which part needs synchronous UX and which can be asynchronous?
  8. What is the expected volume, burst pattern and latency budget?
  9. What evidence must exist for audit or incident investigation?

7.2 Production model interaction

  • Model/provider abstraction only where it serves a real fallback, cost, sovereignty or capability need.
  • Timeouts, rate-limit handling and admission control.
  • Prompt/version identifiers attached to traces.

  • Cost and latency budgets by workflow, not merely per model call.
  • Durable task identifiers, persisted state, cancellation and idempotent resume for long-running work.

7.3 Tool use and MCP

MCP is an important interoperability layer, but an FDE should understand the boundary rather than merely install servers. The 2026-07-28 specification is stateless at the protocol layer: version and capability information travels in request metadata rather than a required initialization handshake. Long-running work is handled through an optional Tasks extension, not assumed session state. Treat every tool invocation as a versioned, security-sensitive distributed-systems operation.

  • Pin the protocol version and compatibility-test clients, servers and gateways before rollout.
  • Use durable application state or the Tasks extension for polling, cancellation, retries and re-entry.
  • Support multi-round-trip input when a task enters input_required; never confuse waiting for input with success.
  • Treat server metadata and tool descriptions as untrusted unless the server and its supply chain are trusted.
MCP is a protocol, not an architecture waiver. The application still owns identity, authorization, tenancy, idempotency, audit, failure recovery and user consent. Separate those durable controls from any one MCP implementation or protocol version.
Never confuse “the model selected a tool” with “the model is authorized to execute the action.” Policy and authority belong outside the model.

Assignment 7A — Agent with an irreversible edge

6–10 hours

Build an approval-gated action agent

Create an agent that can read records and propose an update, but cannot commit the update without an external approval token.

  • Separate plan from commit.
  • Persist the proposed payload and its hash.
  • Invalidate approval if the payload changes.
  • Make the commit idempotent.
  • Trace model call → tool decision → approval → side effect.

Failure injection: crash after the external side effect but before local acknowledgement. Reconcile safely.

Explain to a sponsor why you might not use an agent at all, even though they asked for one.
Banned words: agent, multi-agent, LLM

Model answer (open after you have tried)

An agent decides its own steps, which is powerful but harder to predict, test and control. Many tasks follow a known sequence, so ordinary code with one AI step for the hard part, such as reading a document or drafting a reply, is cheaper, faster and safer. I use the simplest structure that does the job and add freedom only where the task genuinely needs it and we can measure that it helps.

7A. Practical: one workflow, multiple providers

Purpose: make provider differences visible while preserving the workflow's quality, authority and data boundaries. This is a learning exercise, not customer-deployment evidence.

  1. Choose a small extraction-and-proposal workflow. Define typed inputs, a validated output schema, an explicit failure result, deadline, spend limit and permitted data locations. Keep the consequential commit in application code.
  2. Implement two real adapters where access permits, choosing among OpenAI, Claude, Google's supported platform APIs or a local open-weight model. An optional third may be a test double, clearly labelled; if no external access is available, mock the transport and report contract testing only.
  3. Record supported structured outputs, tools, streaming, cancellation, rate limits and usage fields per adapter. Preserve provider-specific metadata behind a common result envelope; do not silently discard unsupported requirements.
  4. Run the same held-out cases through each route. Compare accepted outcomes, schema failures, latency, attempts and total cost. Record model and API versions, dataset version and untested capabilities. Estimate missing cost fields explicitly rather than reporting zero.
  5. Route only among providers approved for this data and task. Inject throttling, malformed output, a missing capability, cancellation and a timeout after an external action. Demonstrate bounded retry, fail-closed policy checks and unknown-outcome reconciliation.

Explain to a sponsor why changing AI provider is more than changing a setting.

Model answer (open after you have tried)

Different providers’ models follow instructions, format answers, refuse requests and handle long inputs differently, and they may process data in different places and charge differently. 10.3 Security pre-flight patterns

  • Data minimization applied before model invocation.
  • Sensitive data detection/redaction/tokenization tested where required.
  • Private connectivity used where network policy requires it; for example, managed model services can expose private endpoints rather than public internet paths.
  • Managed workload identities or equivalent used instead of long-lived embedded credentials.
  • Tool permissions follow least privilege and tenant boundaries are enforced before retrieval/action.
  • Tools, skills, plugins and servers are allowlisted, version-pinned and backed by provenance and compatibility checks.
  • Consequential writes pass deterministic policy and, where required, external approval.
  • Prompt/tool output is treated as untrusted input; injection cannot expand authority.
  • Logs/traces avoid secrets and prohibited sensitive content.
  • Monitoring correlates suspicious credential and tool activity across tasks where policy and privacy requirements allow it.
  • Customer-controlled storage, keys and audit boundaries are used where sovereignty or regulatory requirements demand them.
  • Required security/privacy/risk reviews are complete and residual risks have an authorized owner.

12A. The Six Production Gates

A technically impressive deployment should not scale until it has evidence across all six gates. A failure in any one gate can make the whole system unfit for production.

1. VALUEDoes solving this workflow matter enough to justify the intervention?
2. QUALITYDoes the system perform the intended task at an acceptable level?
3. SAFETYIs the system authorized, bounded and governed for what it can influence?
4. OPERABILITYCan operators deploy, observe, debug, recover and change it safely?
5. ECONOMICSIs cost per successful outcome viable at expected scale?
6. ADOPTIONWill the real workflow use, trust and improve the system?
VALUE → QUALITY → SAFETY → OPERABILITY → ECONOMICS → ADOPTION
  │        │         │          │             │           │
why?     works?    allowed?    runnable?     viable?     used?
Do not compensate for one failed gate by polishing another. Better prompting does not fix a useless workflow; stronger infrastructure does not fix unsafe authority; low token cost does not fix zero adoption.

12.1 Discover

Observe the workflow and gather evidence. Separate what users say happens from what telemetry/process data shows actually happens.

12.2 Frame

Choose an MVP that can falsify the value hypothesis quickly. Write explicit non-goals.

12.3 Build

Prefer a thin vertical slice across real systems to a polished isolated prototype.

12.4 Deploy

Identity, observability, failure handling, data governance and adoption are part of the solution, not “hardening later.”

12.5 Measure

Measure both system quality and workflow outcome. A high eval score with zero adoption is not success.

12.6 Accept and hand off

Treat production acceptance as an explicit gate: named service and workflow owners, runbook and escalation path, access and credential transfer, support boundaries, rollback drill, acceptance evidence and a dated scale / hold / stop decision.

12.7 Codify

Turn the deployment into reusable assets: reference architecture, tool adapter, eval harness, migration checklist, discovery template, runbook or product feedback.

13.1 AI unit economics

The useful denominator is not “per API call.” Measure the cost of achieving a successful workflow outcome.

Cost per successful outcome
=
model inference
+ retrieval / reranking
+ tool / external API cost
+ infrastructure
+ retries / failed attempts
+ human review / correction
+ observability
+ support / operations
Route to the least expensive architecture that passes the required eval and risk gate. A cheaper model can be more expensive overall if it creates retries, escalations, rework or poor adoption.

Cost optimization order

  1. Do not invoke an LLM where deterministic code is sufficient.
  2. Remove context the task does not need.
  3. Reuse safe deterministic/prefix/prompt-cacheable computation where available.
  4. Route simpler tasks to smaller/cheaper models only after eval evidence.
  5. Batch work that does not require interactive latency.
  6. Bound retries, agent loops, output length and tool fan-out.
  7. Optimize retrieval and external tool calls, not just model tokens.
  8. Measure cost per successful task and project it at expected volume.
  9. Compare self-hosted inference on full utilization + operations cost, not GPU price alone.
Semantic caching is not automatically safe. Permission-sensitive, tenant-specific, personalized or rapidly changing answers can make semantic reuse a correctness or authorization defect. Treat cache keys, freshness and authorization scope as part of the security model.

18.0a Four drills the generic questions miss

D1. Decomposition, 60 minutes, no code — “Sync two employee-record systems.”

Spend the first third clarifying: who uses each system, which is authoritative for which field, update frequency, conflict rules and what “synced” means to the business. Name assumptions and missing data aloud. Sequence by risk, propose a thin first slice, sketch the data and APIs, then name failure modes (duplicates, partial writes, identity mismatch). Other reported prompts: improve city traffic; let several teams query a shared dataset without exposing raw records.

D2. Learning round, 60 minutes — extend an unfamiliar library from its documentation.

Pick any small open-source library you have never used. Give yourself 10 minutes to read its docs, then add a feature in three short stages. Ask purposeful high-level questions rather than many syntax questions. Reasoning and navigation are scored more than exact syntax.

D3. Customer simulation, 30 minutes — a sceptical executive whose last AI pilot failed.

Have a partner play the executive. Ask about the business outcome and its owner, where the data lives and what was tried before. Restate the constraint, propose a narrow first slice with one success measure, and state honestly what you will not promise. Practise delivering bad news: “The deployment is three weeks late; the CTO has joined the call.”

D4. Timed take-home, five hours — build and defend.

Use a vague brief (for example, the §11 misleading brief). Build the smallest useful slice with timeouts, rate-limit handling, malformed-output handling, tests and a ten-case eval. Then record a ten-minute defence: one sentence per design decision, what you left out and why, and what you would do next. A well-scoped build you can defend beats a larger one you cannot.

18.1 Coding / practical engineering

Q1. Implement a rate-limited concurrent API client.

Look for bounded concurrency, timeout, retry policy, error handling, testability and observability—not clever syntax.

Q2. An upstream API occasionally returns success after your client times out. How do you prevent duplicate writes?

Discuss idempotency keys, operation identity, external status reconciliation and unknown-outcome handling.

Q3. Review a Python service that retries every exception five times.

Classify transient/permanent errors, retry budget, backoff/jitter, deadlines and observability.

18.2 System design

Q4. Design an AI-assisted claims workflow used by 5,000 operators.

Start with system of record, authorization, workflow steps and SLAs before model choice.

Q5. Design a long-running agent that may wait 24 hours for human approval.

Persist state, durable waiting, fresh authorization, retries, deadlines, fencing/idempotency and audit.

Q6. How would you deploy across customers with different data residency requirements?

Discuss tenancy, regional deployment, provider/model options, data flow, key management and operational complexity.

18.3 AI / agent engineering

Q7. When should you not use an agent?

When deterministic workflow or single model call gives sufficient flexibility with lower reliability/operational risk.

Q8. Your RAG answer quality is poor. What do you inspect first?

Build labeled examples; separate retrieval from generation; inspect source freshness, authorization filters, chunking, query formulation, ranking and context assembly.

Q9. How do you evaluate a tool-using agent?

Task outcome, tool selection, argument correctness, sequence, policy compliance, side-effect integrity, latency/cost and recovery.

18.4 Customer ambiguity

Q10. The customer insists on multi-agent architecture. What do you do?

Understand the desired capability and why they believe multi-agent is necessary; propose a falsifiable simpler baseline and compare on quality/latency/cost/operability.

Q11. The executive sponsor wants production in two weeks; security says six months.

Find a low-risk vertical slice, constrain data/actions, use sandbox/read-only or approval-gated mode, define evidence required to expand.

Q12. Your prototype works but users do not adopt it.

Investigate workflow friction, trust, incentives, timing, UX and whether the solved problem was actually valuable; do not simply tune the model.

Field Kit — scripts & deployment cards ↑ top

These are designed to be used during an engagement, not memorized.

Field script 1 — “Just make it autonomous”

Customer

“We don't want people reviewing this. Make the agent autonomous.”

FDE

“Let's separate where autonomy creates value from where it creates irreversible risk. For the first deployment, I recommend the agent run the whole workflow but require approval at the commit boundary. That gives us production data on quality, latency and intervention rate. If approvals become unnecessary in almost all eligible cases and the risk gate remains green, we have evidence for increasing autonomy.”

Field script 2 — “We need multi-agent”

Customer

“Our architecture must be multi-agent.”

FDE

“What capability do you expect multiple agents to unlock that one workflow cannot? I suggest we establish a simpler baseline first, then compare decomposition only if it improves task success, latency, cost or maintainability. That gives us evidence rather than making topology the requirement.”

Field script 3 — “Security won't allow an external model”

Security

“No enterprise data can go to a public AI endpoint.”

FDE

“Understood. Let's identify the exact data and network constraints first. We can evaluate regional/private managed endpoints, a dedicated environment or self-hosted inference. I’ll document the data path, retention, identity and egress controls so we can choose the least operationally expensive option that satisfies the policy.”

Field script 4 — “The demo looks accurate; why do we need evals?”

Sponsor

“We've tried twenty examples and it works. Why slow down for evals?”

FDE

“Those twenty examples are evidence, but they are not a release gate. We'll turn representative normal and failure cases into a small repeatable suite. That lets us change prompts, models or retrieval later without rediscovering quality problems in production.”

Field script 5 — “Use the biggest model everywhere”

Team

“Quality matters, so route everything to the strongest model.”

FDE

“We'll use the strongest model to establish the quality ceiling. Then we'll test smaller routes against the same eval set. Anything cheaper only ships if it still passes the task and risk gates. The decision metric is cost per successful outcome, not model price alone.”

Production pre-flight

  • Value: workflow owner, baseline, target and eligible volume documented.
  • Quality: representative eval set passes the release threshold.
  • Authority: read/write scopes, approval boundaries and idempotency verified.
  • Data: classifications, tenant boundaries, retention and sensitive-data handling verified.
  • Reliability: timeouts/retries bounded; failure injection and rollback completed.
  • Observability: end-to-end task correlation, model/tool versions, cost and latency visible.
  • Security/governance: required reviews complete; residual risk has an authorized owner.
  • Economics: cost per successful outcome and expected-scale projection reviewed.
  • Adoption: rollout stage, champion users, feedback and escalation paths defined.
  • Operations: runbook owner can diagnose and recover the service without the original author.

Engagement closeout card

  • What changed in the user workflow?
  • Which Six Production Gates passed, failed or remain uncertain?
  • What production evidence supports the conclusion?
  • What should not be automated or scaled yet?
  • What did users override, distrust or work around?
  • What is the current cost per successful outcome?
  • What reusable architecture, tool, eval or playbook came out of the engagement?
  • What is the next GO / HOLD / STOP decision and who owns it?
