IAM Building Blocks

Concept Use it for Exam clue

IAM group Permission management for collections of users Groups cannot be nested and do not contain roles
IAM role Temporary credentials for services, applications, federation, and cross-account access Preferred over embedded access keys

Policy Evaluation Shortcut

  1. Start with implicit deny.
  2. An applicable explicit allow can grant access.
  3. Any applicable explicit deny wins.
  4. Effective permissions are constrained by identity/resource policies, SCPs, permission boundaries, and session policies.

Account Security Pattern

AWS Organizations
├── Management account: billing and organisation administration only
├── Security OU: log archive + security tooling
├── Infrastructure OU: shared networking and platform accounts
└── Workload OUs: production / non-production accounts

Human access → IAM Identity Center → permission sets → short-lived role sessions
Workload access → IAM role → temporary credentials from STS

Shared Responsibility Shortcut

  • AWS is responsible for security of the cloud: facilities, physical hardware, foundational infrastructure, and managed-service infrastructure.
  • You are responsible for security in the cloud: data, identities, permissions, configuration, encryption choices, and guest OS/application patching where you control the OS.
  • The customer share generally decreases as you move from self-managed EC2 toward more managed/serverless services, but data classification and access control remain customer responsibilities.

High-Yield Rules

  • Protect the root user with MFA and use it only for root-only tasks.
  • Prefer IAM Identity Center/federation for workforce access; use Cognito for application end users.
  • Prefer roles and temporary credentials over access keys.
  • Use AWS Organizations and SCPs as organisation guardrails.
  • Centralise logs in a separate log archive/security account.
  • Use AWS Resource Access Manager to share supported resources across accounts.

30-second recall: Identify the principal, action and resource; check grants and limiting policies. Workforce SSO, customer sign-in and workload credentials are different problems.

Explain it: mechanism, trade-off and a changed requirement

Authentication establishes identity; authorization decides whether that identity may perform this action on this resource. A role trust policy controls assumption, not the subsequent S3 or KMS operation. A permissions boundary does not grant actions. Cross-account access needs the relevant permissions in both accounts. Explicit denies override allows. Avoid a universal “intersect every policy” mnemonic: same-account resource grants behave differently depending on whether they target a user, role or session principal. For exam reasoning, state the principal type and request first.

Worked decision: A supplier needs temporary access to one reporting bucket. Use a constrained cross-account role and the required trust/caller permissions; authorize only the reporting operations. Copying a long-lived administrator key creates excessive access and credential-management work.

Change one requirement: Employees now need SSO across several AWS accounts: use Identity Center permission sets. Customer sign-up for the reporting application instead points to Cognito; it is not solved by giving every customer an IAM user.

Public vs Private Subnet

A subnet is considered public when its route table has a route to an Internet Gateway. A public IP alone is not enough. Private workloads normally use a NAT gateway for IPv4 outbound internet access or VPC endpoints for private AWS service access.

Security Group vs Network ACL

Security group Network ACL
Stateful Stateless
Applied to ENIs/resources Applied at subnet boundary
Allow rules only Allow and deny rules
All rules evaluated together Rules processed in number order
Return traffic automatically allowed Return traffic must be explicitly permitted

Connectivity Choices

Need Best fit
Connect a small number of VPCs VPC peering; non-transitive
Hub-and-spoke for many VPCs/on-prem networks Transit Gateway
Private access to a provider service AWS PrivateLink / interface endpoint
Private access to S3 or DynamoDB Gateway endpoint

Dedicated, consistent hybrid connection Direct Connect; add VPN for encryption when required

30-second recall: Trace both directions: DNS, route, network controls, service authorization. “Private” is not equivalent to “permitted.”

Explain it: mechanism, trade-off and a changed requirement

A route selects the next hop; a security group permits traffic to a resource; a NACL filters packets at a subnet boundary. For a connection started by the application, stateful SGs allow the corresponding return traffic, while stateless NACL rules must permit the return ports. An S3 gateway endpoint adds a service route; its policy limits access but cannot supply missing IAM/bucket permissions. Interface endpoints have private ENIs, SGs and DNS considerations. Public IPv4 connectivity requires the appropriate addressing and route, not merely a subnet name.

Worked decision: An app in a private subnet reads S3 and needs no public internet access. Use an S3 gateway endpoint, associate the actual app route table and validate both endpoint and S3 permissions. A NAT gateway creates an unnecessary public-service path and cost for this requirement.

Change one requirement: The app must also reach an external vendor API. The S3 endpoint does not provide that egress; design the separate outbound path. If only a partner service must be exposed privately, evaluate PrivateLink rather than connecting all VPC routes.

5. Encryption and Secrets

KMS Choices

Key type Ownership and control Rotation
AWS owned key AWS owns and manages; not visible in your account Managed by the AWS service
AWS managed KMS key Visible in your account but managed by AWS service AWS rotates key material annually
Customer managed KMS key You control policy, grants, lifecycle, aliases, and rotation Optional automatic/custom-period or on-demand rotation for supported symmetric keys
CloudHSM/custom key store Dedicated HSM control and specialised compliance More control and more operational responsibility

Encryption Patterns

  • At rest: S3 SSE-S3/SSE-KMS, EBS encryption, RDS/Aurora encryption, DynamoDB encryption.
  • In transit: TLS certificates from ACM, HTTPS, VPN, encrypted Direct Connect overlay when required.
  • Envelope encryption: Data encrypted with a data key; data key encrypted by a KMS key.
  • Cross-account KMS: Key policy must allow the external account, and its IAM policy must allow use.
  • EBS: Enable encryption by default; encrypt existing data by snapshot/copy/restore workflows.

Secrets Manager vs Parameter Store

Secrets Manager Systems Manager Parameter Store
Built-in rotation integrations and secret lifecycle Configuration and hierarchical parameters
Designed for credentials/API keys Standard/SecureString parameters
Higher feature set and cost Standard tier can be lower cost
Use when rotation is a core requirement Use for configuration or simpler secret storage

30-second recall: Separate data permission, key permission and transport encryption. Secrets Manager stores secret values; KMS governs cryptographic operations.

Explain it: mechanism, trade-off and a changed requirement

For an encrypted S3 object, GetObject and the required KMS permission are separate checks. Envelope encryption uses a data key for the object and protects that data key with a KMS key. Rotating key material does not require re-encrypting every old object immediately; old ciphertext must remain decryptable. TLS protects transport, not the stored copy. An explicit bucket policy requiring a selected key can reject a request even when bucket-default encryption exists.

Worked decision: A reporting role lists a bucket but cannot read its SSE-KMS objects. Inspect object-level S3 grants and KMS key authorization separately. Adding a NAT route or widening ListBucket cannot repair missing decrypt permission.

Change one requirement: The issue is rotating a database password, not decrypting an object. Use a secret-management rotation flow and update application credential retrieval; rotating a KMS key does not change that password.

Common trap: CloudTrail answers who called which API and when. CloudWatch answers metrics, logs, alarms, and operational visibility. AWS Config answers what the resource configuration was and whether it complied.

30-second recall: Select the control by its job: prevention, detection, investigation or evidence.

Explain it: mechanism, trade-off and a changed requirement

WAF evaluates web requests; it does not patch a vulnerable container. Inspector finds supported workload vulnerabilities; it does not replace a web firewall. GuardDuty detects suspicious activity, while Macie focuses on sensitive S3 data. CloudTrail records API activity; Config evaluates recorded resource configuration. Detection is not remediation: state which automation or operator responds, and with what permissions. A sample finding proves the finding pipeline, not an actual attack detection test.

Worked decision: A team asks who removed encryption from a resource and whether the resource is compliant. Combine API audit evidence with configuration history/rules. A CPU alarm cannot identify the actor or determine the relevant compliance rule.

Change one requirement: The requirement becomes blocking a particular malicious HTTP header before origin access. Choose an appropriate WAF rule and test the request/action, not just the existence of a security finding.

7. Availability, Durability, and Fault Tolerance

Term Meaning
Availability System is accessible and functioning
Durability Data remains intact over time
High availability Minimise downtime through redundancy and failover
Fault tolerance Continue operating despite component failure, usually with little/no interruption
RTO Maximum acceptable time to restore service
RPO Maximum acceptable data loss measured in time

Multi-AZ vs Multi-Region

  • Multi-AZ: Handles data-centre/AZ failure, lower latency, common default for HA.
  • Multi-Region: Handles Region failure, supports global users/data residency, but increases cost and complexity.
  • Start with the required RTO/RPO and business impact; do not select Multi-Region automatically.

Reliability Controls Often Missed

ConcernDesign response
Service quotas / throttlingKnow expected scale, request quota increases before failover events, use backoff/retries, queues, and load shedding where appropriate.
Configuration driftPrefer repeatable infrastructure definitions and automated deployment; immutable replacement is safer than manual in-place repair when feasible.
Single points of failureDistribute across AZs, use health checks and automated failover, and remove state from individual compute instances.
Recovery confidenceBack up data, define retention, and test restore/failover procedures against the required RTO/RPO.

30-second recall: RTO measures time to restore useful service; RPO measures acceptable lost changes. Redundant compute does not make stale data current.

Explain it: mechanism, trade-off and a changed requirement

Start recovery planning with all required state stores and dependencies. A database may recover quickly while missing object data or secrets still prevents service. Backups need restoration; replication reduces some recovery work but can propagate unwanted changes. Pilot light keeps essential components ready; warm standby keeps a reduced but working stack. Region recovery also needs quotas, capacity, keys, routing and a tested runbook. The strategy names imply relative effort/cost, not guaranteed recovery times.

Worked decision: A portal permits ten minutes of downtime and five minutes of lost writes. A daily snapshot alone fails the data-loss requirement even if replacement EC2 instances launch in one minute. Evaluate replication/backup frequency, then measure data-backed recovery.

Change one requirement: The business permits a full day of downtime and an earlier daily copy. Backup/restore may now meet the requirement at lower ongoing cost; an always-running secondary stack needs justification.

Auto Scaling Components

  • Launch template: AMI, instance type, security groups, user data, IAM instance profile.
  • Auto Scaling group: minimum, desired, maximum, subnets/AZs, health checks.
  • Scaling policies: target tracking, step, scheduled, predictive.
  • Prefer target tracking when a meaningful utilisation metric exists.
  • Use ELB health checks when the application can fail while the EC2 instance remains running.
CloudWatch metric → scaling policy → ASG changes desired capacity
                                      │
                                      └→ instances register/deregister with load balancer

30-second recall: Load balancing distributes traffic; health checks remove bad targets; scaling changes capacity. Test all three separately.

Explain it: mechanism, trade-off and a changed requirement

A running process can return a healthy response while its database is unavailable. Define health checks and business probes with different purposes. Scale on a metric correlated with useful demand: CPU for CPU-bound work, request load for suitable web services, or backlog per worker for a queue. Cooldowns and startup time mean scaling is not instantaneous. Minimum capacity protects availability; maximum capacity limits spend but can leave requests queued or rejected. Adding workers can overload the database if it is the bottleneck.

Worked decision: Two tasks serve an API in different AZs. Stop one, measure failed requests and recovery, and confirm the remaining target still serves data. This establishes a task-loss observation; it does not emulate every consequence of an AZ outage.

Change one requirement: Queue age rises while CPU stays low. Investigate dependency latency and backlog per worker rather than simply raising a CPU target. Protect the downstream connection limit when scaling.

9. Decoupling and Event-Driven Design

SQS vs SNS vs EventBridge vs Kinesis

Service Delivery model Best fit
SQS Standard Pull queue, at-least-once, best-effort order Buffering and decoupling independent workers
SQS FIFO Pull queue, ordered within message group, deduplication Ordered workflows and exactly-once processing semantics
SNS Push pub/sub topic Simple fan-out to subscribers/endpoints
EventBridge Event bus with rules, filtering, schemas, SaaS/AWS integration Event routing across services/accounts and scheduled events
Kinesis Data Streams Ordered records per shard/partition key, replay/retention High-throughput real-time stream processing
Amazon Data Firehose Managed delivery stream Deliver/transform streams into destinations such as S3 and Redshift
Amazon MQ Managed ActiveMQ/RabbitMQ Migrate applications that require traditional broker protocols

Queue Reliability Rules

  • Set visibility timeout longer than normal processing time.
  • Use a dead-letter queue for repeated failures.
  • Make consumers idempotent because duplicate delivery can occur.
  • Long polling reduces empty receives and cost.
  • Use SNS → multiple SQS queues for durable fan-out to independent consumers.

Workflow Choice

  • Step Functions: Orchestrate multi-step workflows, retries, branching, and state.
  • SQS: Buffer independent asynchronous work.
  • EventBridge: Route events based on content.
  • API Gateway: Managed front door for REST/HTTP/WebSocket APIs.

30-second recall: A queue absorbs bursts; idempotency protects business effects; an outbox coordinates state with eventual publication.

Explain it: mechanism, trade-off and a changed requirement

SQS hides a received message during its visibility timeout; processing is not acknowledged until deletion. A consumer that crashes after a successful business commit can receive the same work again. FIFO deduplication/ordering has a defined scope and does not make arbitrary external effects atomic. Write the business state and durable deduplication marker together where transactions permit. An outbox records publication intent in that transaction; publication can repeat, so downstream consumers still need idempotency. DLQs isolate repeated failures but require diagnosis and deliberate redrive.

Worked decision: An inventory worker decrements stock and crashes before acknowledgement. On retry, a committed order marker must prevent a second decrement. A marker written before an independent stock update can instead lose work if a crash happens between them.

Change one requirement: Two analytics applications must independently reread the last hour. A retained stream with separate consumer positions fits; a single work queue from which messages are deleted does not provide that replay contract.

10. Storage Resilience

Storage Decision Table

Need Service
Object storage/data lake/static assets S3
Block device for EC2/database EBS
Shared Linux NFS across AZs EFS
Windows file shares / Lustre / NetApp / OpenZFS FSx family
Temporary highest-speed local scratch EC2 instance store
Hybrid file/volume/tape integration Storage Gateway

EBS Essentials

  • EBS volumes are created in one AZ and attach to instances in that AZ.
  • Snapshots are incremental and stored in AWS-managed S3 infrastructure.
  • Restore a snapshot into another AZ; copy snapshots across Regions/accounts when needed.
  • gp3: general-purpose SSD with independently configurable capacity, IOPS, and throughput.
  • io2 Block Express: critical I/O-intensive workloads with higher durability/performance.
  • st1: throughput-optimised HDD for large sequential workloads.
  • sc1: lowest-cost HDD for infrequently accessed sequential data.
  • Instance and volume limits both affect achievable performance.

S3 Resilience Features

  • Strong read-after-write consistency for PUT, overwrite, DELETE, and LIST operations.
  • Versioning protects against accidental overwrite/deletion.
  • Cross-Region Replication or Same-Region Replication requires versioning.
  • Object Lock provides WORM retention in governance or compliance mode.
  • MFA Delete adds protection but has operational constraints.
  • Multi-Region Access Points can route requests across replicated buckets.

30-second recall: Choose the interface and failure boundary first: object API, block device, shared file system, then protection.

Explain it: mechanism, trade-off and a changed requirement

EBS persistence does not mean cross-AZ attachment: recover a volume in another AZ from a snapshot. Instance store is tied to instance lifecycle and should hold reconstructable data. EFS provides shared file access; an EBS Multi-Attach design requires supported volumes and coordinated writers rather than behaving like an ordinary shared NFS service. S3 versioning preserves versions; replication creates copies; Object Lock applies retention/legal hold. These mechanisms solve different failure or compliance cases and can be combined.

Worked decision: Two Linux app instances in different AZs need the same mutable file directory. Regional EFS fits the shared file interface. Copying an EBS snapshot every minute does not provide a concurrently shared directory.

Change one requirement: The objects must remain immutable for a retention period. Select an appropriate S3 Object Lock policy and permissions. A versioned but freely deletable history alone does not satisfy the immutability requirement.

DeploymentTopologyRead trafficPrimary purpose

Exam trap: “Multi-AZ cannot serve reads” is only safe shorthand for the classic Multi-AZ DB instance deployment. Multi-AZ DB clusters have readable standbys. Replica counts and capabilities vary by engine; Aurora supports up to 15 Aurora Replicas, so do not memorise one fixed number for every RDS engine.

Aurora Essentials

  • MySQL- and PostgreSQL-compatible managed relational database.
  • Shared distributed storage spans multiple AZs.
  • One writer endpoint plus reader endpoint(s); add Aurora Replicas for reads/HA.
  • Aurora Serverless v2 scales capacity within configured minimum/maximum ACUs.
  • Aurora Global Database uses one primary Region and read-only secondary Regions; plan explicit switchover/failover.
  • RDS Proxy pools and manages connections for Lambda/high-connection workloads.

DynamoDB Essentials

  • Fully managed key-value/document database with single-digit millisecond performance.
  • On-demand: unknown/spiky traffic; pay per request.
  • Provisioned: predictable traffic; configure RCU/WCU and auto scaling.
  • Global secondary indexes support alternate access patterns.
  • DynamoDB Streams captures item-level changes.
  • Global Tables provide multi-Region, multi-active replication; choose MREC (eventual) or MRSC (strong) consistency deliberately.
  • DAX provides in-memory read acceleration for compatible access patterns.
  • Use TTL for asynchronous cleanup after expiry and PITR for continuous backups.

DR Strategy Ladder

Strategy Typical relative cost RTO/RPO direction What stays running
Backup and restore Lowest Hours; depends on backup frequency Backups only
Pilot light Low Tens of minutes to hours Core data/services

30-second recall: Diagnose the bottleneck: availability, read load, write load, connections or freshness.

Explain it: mechanism, trade-off and a changed requirement

A classic RDS Multi-AZ DB instance uses a standby for failover, not normal read traffic. A read replica is a separate readable copy, commonly asynchronous, so read freshness must be evaluated. A Multi-AZ DB cluster has readable instances; avoid applying the classic rule to it. RDS Proxy pools connections; it does not cache SQL results or make expensive queries cheap. Aurora replicas and reader endpoints provide another relational topology; distinguish adding readable capacity from changing the writer workload.

Worked decision: Reporting saturates the primary and can tolerate lag. Route reporting to a read replica, keep transactions on the writer and observe ReplicaLag. Merely adding Proxy addresses a different problem unless connection churn is also the bottleneck.

Change one requirement: The report must see the just-committed transaction. An asynchronous replica is not a universal read-after-write guarantee; use a suitable authoritative read path or a supported consistency design and reassess capacity.

30-second recall: IOPS, throughput and latency are different measurements; the instance can limit the volume.

Explain it: mechanism, trade-off and a changed requirement

Plan TTLs, invalidation, eviction, and stale-data tolerance. A cache improves performance but adds consistency considerations.

30-second recall: A cache trades freshness and extra operating cost for fewer reads or lower latency. Define invalidation before claiming success.

Explain it: mechanism, trade-off and a changed requirement

In cache-aside, the application checks cache first, reads the database on a miss and fills the cache. Updating the database does not automatically update that entry. A TTL limits lifetime but cannot promise that every read sees the newest write. Invalidation has races; correctness-sensitive reads may need to bypass the cache. Worked decision: A catalog tolerates one minute of staleness and repeatedly reads the same products. Cache-aside with a deliberate TTL/invalidation policy can fit. Measure cache hit ratio and origin load before judging the cost benefit.

Change one requirement: The cached value is available inventory at checkout and overselling is forbidden. Validate the authoritative update atomically; cached display data cannot enforce that business invariant.

21. Network Cost Optimisation

  • Data-transfer prices vary by service, Region, direction, and AZ; do not rely on one universal per-GB number.
  • Cross-AZ traffic often incurs charges on one or both sides; design chatty components carefully.
  • VPC endpoints can reduce NAT gateway processing charges for supported AWS services.
  • Use gateway endpoints for S3/DynamoDB when appropriate; no hourly endpoint charge.
  • NAT gateway vs NAT instance: NAT gateway is managed, scalable, and usually the lower-operations answer; a NAT instance can be cheaper for very low throughput but requires EC2 sizing, patching, HA, and failover design.
  • For zonal NAT, a shared gateway reduces count but can add cross-AZ cost and a shared failure dependency; same-AZ gateways preserve egress independence. Regional NAT is a separate current availability mode with automatic AZ expansion; verify its behavior and pricing rather than applying the zonal rule universally.
  • CloudFront can reduce origin load and internet egress patterns for cacheable content.
  • Keep data processing near the data when possible.
  • Use Cost Explorer and the Cost and Usage Report to validate actual transfer paths.

30-second recall: Draw the charged traffic path and distinguish fixed hourly from usage charges.

Explain it: mechanism, trade-off and a changed requirement

An hourly gateway or interface endpoint can cost money with no traffic. Gateway endpoints for supported S3/DynamoDB paths avoid NAT processing for that traffic. Interface endpoints incur their own charges and need sufficient AZ coverage. Cross-AZ traffic can add costs; eliminating it must not silently remove required resilience. Zonal NAT and Regional NAT have different availability behavior. Always calculate the selected mode and Region rather than transplanting one per-GB rate to every path.

Worked decision: A private application sends its bulk S3 traffic through a NAT gateway. Evaluate a gateway endpoint and policy/route changes, then compare the affected traffic cost. The NAT may still be required for other destinations; endpoint adoption does not automatically remove its fixed charge.

Change one requirement: The application instead calls a supported private API with little traffic across three AZs. Include all interface endpoint-hours before declaring it cheaper; privacy may justify it even when it is not the cheapest option.

24. Frequent Exam Traps

  1. Classic RDS Multi-AZ DB instance is for HA; read replicas are for read scaling. But an RDS Multi-AZ DB cluster has readable standby DB instances.
  2. IAM Identity Center is for workforce access; Cognito is for application end users.
  3. SCPs do not grant permissions. They restrict maximum permissions.
  4. Security groups are stateful; NACLs are stateless.
  5. A NAT gateway does not allow unsolicited inbound internet traffic.
  6. VPC peering is non-transitive. Use Transit Gateway for hub-and-spoke at scale.
  7. CloudFront caches; Global Accelerator accelerates network paths without caching.
  8. EBS is AZ-scoped; EFS is shared file storage; S3 is object storage.
  9. RDS Proxy manages connections; ElastiCache caches data.
  10. SQS Standard can deliver duplicates and does not guarantee strict order.
  11. S3 replication requires versioning and is not a substitute for every backup/retention requirement.
  12. Direct Connect is not encrypted by default.
  13. Regional RIs and Savings Plans do not reserve capacity; zonal RIs include a reservation in the specified AZ.
  14. Avoid hard-coded service quotas and prices unless the question states them. Many vary by engine, Region, account, or configuration.
  15. Do not choose a complex self-managed solution when the question says least operational overhead.
  16. Do not choose Multi-Region solely because it sounds more resilient; match RTO/RPO and cost.
  17. Recognise current naming: Amazon Quick is the current product name; Quick Sight is its BI feature; older study material may use QuickSight or QuickSuite.
  18. Elastic Transcoder is a legacy-scope anomaly: it is still named by the live SAA-C03 in-scope page despite AWS discontinuing the service in November 2025. Know what it was for, but do not choose it as a modern architecture recommendation.

  • TTL: asynchronous cleanup of expired items; useful for sessions, temporary records, and retention patterns.
Explain keys, capacity, consistency and hot partitions

A partition key defines a distribution/access boundary; a sort key orders related items within that key. Query selects a partition-key value, optionally narrowing by sort key. Scan examines the wider table/index and filters afterward. A GSI supplies alternate keys but adds writes/storage and supports eventual reads. A strong base-table read does not make a preceding GSI lookup strongly consistent.

For separate reads of a 6 KiB item, round to two 4 KiB units: one strong read uses two read units, an eventual read one. Ordinary writes round to 1 KiB units, so that item needs six write units. Transactions and indexes change the calculation. A hot key is uneven traffic, not merely insufficient total table capacity; changing partition design may matter more than buying capacity.

Conditional writes protect item-level assumptions. Use transactions when multiple related writes must commit together. TTL removes expired data asynchronously, so the application enforces time-sensitive expiry. Global Tables mode determines cross-Region consistency; do not transfer MREC assumptions to MRSC. 32. Cost Architecture Decision Rules

Cost optimisation is an architecture sequence

1
Remove waste. Delete idle/unattached resources before negotiating discounts.
2
Right-size. Match instance, DB, storage, and provisioned capacity to real workload.
3
Make demand elastic. Auto Scaling, serverless, schedules, and queue buffering reduce paid idle capacity.
4
Choose commitment. Savings Plans / Reserved pricing only after baseline demand is understood; Spot for interruptible workloads.
5
Optimise storage and transfer. Lifecycle/tiering, compression, endpoints, CDN, and topology can dominate cost.

Network cost traps

  • Do not send S3/DynamoDB traffic through NAT when a suitable gateway endpoint solves the private-access requirement.
  • Cross-AZ traffic can introduce transfer cost; resilience benefits still come first when HA is required.
  • CloudFront can reduce repeated origin transfer and improve global delivery for cacheable content.
  • For heavy predictable hybrid transfer, compare Direct Connect economics with internet/VPN transfer and operational requirements.
  • For unpredictable workloads, fixed always-on capacity can be more expensive than elastic/serverless designs.

No-purchase cost worksheets

All rates below are fictional teaching inputs, not AWS prices. Work in USD and a 730-hour month. Excluded costs are stated; use current regional pricing and the full inventory for a real decision. A cost worksheet is modeled evidence.

Compute: steady baseline plus interruptible burst

Two workers are needed continuously; four extra workers are needed for 100 hours/month. Assume On-Demand $0.10/worker-hour and Spot $0.03/worker-hour; the burst tolerates interruption and needs 20% extra worker-hours for retries.

Peak fleet all month: 6 × 730 × 0.10 = $438. Elastic all-On-Demand: 2 × 730 × 0.10 + 4 × 100 × 0.10 = $186. Baseline On-Demand plus Spot burst: 146 + 4 × 100 × 1.20 × 0.03 = $160.40. Savings versus elastic On-Demand: $25.60. Add queue/storage/transfer and operational costs before adopting; do not compare against an unavailable Spot guarantee.

Variation: if the burst cannot be interrupted, reject Spot even though its price is lower. Only consider a term commitment after validating the ongoing baseline.

Storage: cheap monthly price, expensive short retention

Keep 100 GB for 10 days. Assume Standard $0.03/GB-month with proportional storage charging; an alternative costs $0.01/GB-month but charges at least 90 days. Use a 30-day month for this worksheet.

Standard storage: 100 × 0.03 × 10/30 = $1. Alternative minimum: 100 × 0.01 × 3 = $3, before transition/retrieval/request charges. The cheaper monthly rate loses. For a 7-year archive, recompute including retrieval SLA, access frequency, retained versions, object sizes and protection.

Variation: instant access can eliminate a delayed-retrieval archive regardless of price. These illustrative rates are not claims about a named AWS class.

Database: utilization and secondary-index cost

Assume provisioned throughput costs $0.20/hour for a fully sized capacity package, or on-demand requests cost $2/million normalized units. Ignore common storage/backup charges only for this comparison. Demand is 20 million units/month.

Provisioned: 730 × 0.20 = $146; on-demand: 20 × 2 = $40. Illustrative break-even: 146/2 = 73 million units. If the access path adds 50% request-equivalent units, on-demand becomes $60. Recalculate provisioned/index headroom too; do not assume the original package can carry the extra load. Actual DynamoDB read/write prices, item rounding and GSI behavior must be priced separately.

Variation: a stable high-volume workload may favor provisioned capacity, but a single hot key or unsupported consistency requirement is a design problem before it is a pricing problem.

Network: endpoint savings depend on what can be removed

Assume a zonal NAT costs $0.05/hour plus $0.05/GB processed. It carries 1,000 GB/month of S3 traffic plus unrelated vendor traffic. Moving the S3 path to a suitable gateway endpoint avoids $50 in assumed NAT processing; it does not save the $36.50 NAT monthly hours if the vendor still needs it.

For a separate interface-endpoint case, assume $0.01/endpoint-AZ-hour plus $0.01/GB. Two AZs with 1,000 GB cost 2 × 730 × 0.01 + 1,000 × 0.01 = $24.60, excluding other transfer charges. That formula is not the price of a gateway endpoint. Compare only equivalent service paths and resilience.

Variation: one centralized zonal gateway may reduce hourly count but add cross-AZ charges and a failure dependency. State the chosen availability mode and traffic topology.

Use hard constraints before feature recall

1

35. Architecture Drills

Reveal the answer only after drawing your own

1 · Private application servers must download objects from S3 without internet/NAT
Answer: S3 gateway VPC endpoint + route-table association + appropriate S3/IAM policies. The endpoint removes the need to route this traffic through a NAT gateway.
2 · An e-commerce API sees sudden bursts that overwhelm the order-processing workers
Answer: decouple ingestion from processing with SQS; scale workers based on queue demand; use retries/DLQ and idempotent consumers.
3 · Global users need faster delivery of cacheable web assets and protection from common web exploits
Answer: CloudFront at the edge with AWS WAF, backed by S3/ALB as appropriate. Global Accelerator is not a content cache.
4 · A relational database must automatically fail over within the Region; reporting also needs read scale

5 · A company has 80 VPCs and on-premises networks and wants central routing instead of a peering mesh
Answer: AWS Transit Gateway hub-and-spoke. VPC peering is non-transitive and becomes operationally complex at this scale.
6 · Security needs to identify which principal changed a production security group yesterday
Answer: CloudTrail for API/account activity; AWS Config is useful alongside it to inspect resource configuration history/compliance state.
7 · A Linux analytics workload needs a very high-performance shared parallel file system linked with S3 datasets
Answer: FSx for Lustre is the first service to evaluate; ordinary EFS is for general shared NFS rather than HPC-style parallel-file workloads.
8 · A company must expose an internal service privately to many consumer VPCs without establishing full network routing between them
Answer: AWS PrivateLink / interface endpoints, rather than full-mesh VPC peering.

Answer aloud before revealing. A correct label without the mechanism is a cue to revisit the explanation.

Role assumption succeeds but GetObject fails. What changes?

A private app cannot read S3. Which four layers do you trace?

Name resolution, route/endpoint selection, network controls where applicable, and service authorization. Inspect the actual route table and principal.

Common mistake: Adding an endpoint and assuming it grants IAM access. Revisit explanation.

Does KMS key rotation rotate a database password?

No. The key protects encryption operations/material; secret rotation changes the credential and requires a working update/retrieval flow.

Common mistake: Conflating keys with secret values. Revisit explanation.

A daily snapshot restores in five minutes. Is RPO five minutes?

No. Restore duration concerns RTO; recoverable write age can approach a day. Inspect every required state store.

Common mistake: Measuring only the time EC2 reaches Running. Revisit explanation.

CPU stays low while a worker queue ages. What do you investigate?

Backlog per available worker, oldest-message age, processing time and downstream constraints. Select a demand-relevant scaling metric.

Common mistake: Scaling only on CPU or adding unlimited database clients. Revisit explanation.

A worker crashes after committing stock but before acknowledging work. What protects it?

Atomic business state and deduplication marker, plus appropriate outbox/consumer idempotency for publication.

Common mistake: Assuming FIFO alone makes every external effect exactly once. Revisit explanation.

Can an ordinary EBS volume provide shared cross-AZ NFS?

No. Choose a suitable shared file service, or restore EBS into another AZ for a recovery workflow.

Common mistake: Confusing snapshot portability with concurrent attachment. Revisit explanation.

Which fixes connection churn, repeated reads and reporting load?

Consider RDS Proxy, a suitable cache, and readable replicas respectively, after checking requirements.

Common mistake: Assuming Proxy caches SQL or a classic standby serves reports. Revisit explanation.

Why is a successful page load weak evidence of CloudFront origin failover?

It may be a cache hit. Use an uncached key, a configured failover condition and distinct secondary content.

Common mistake: Equating CDN origin failover with DNS failover. Revisit explanation.

Does a Glue catalog contain all the data Athena queries?

It supplies metadata; Athena reads the relevant data source. Compare query predicates, partitions, format and actual scanned bytes.

Common mistake: Drawing every data byte as flowing through the catalog. Revisit explanation.

Does a regional RI guarantee capacity in a selected AZ?

No. Distinguish pricing benefit, RI scope and an explicit capacity-assurance requirement.

First-principles practice

A /27 subnet needs 28 ordinary IPv4 workload addresses. Does it fit?
No. A /27 has 32 addresses; AWS reserves five in an ordinary subnet, leaving 27. A /26 provides 59. Include load balancer/endpoint ENIs and growth; do not confuse theoretical CIDR size with usable capacity.
A cross-account role can list a bucket but cannot read SSE-KMS objects. What do you inspect?
Separate S3 ListBucket from GetObject and KMS Decrypt. Cross-account access needs the relevant identity/resource grants and KMS key authorization; explicit denies, SCPs and boundaries can constrain access. A network endpoint creates a path, not permission. Test each layer rather than granting administrator access.
A 6 KiB DynamoDB item is read strongly consistently once per second. What read capacity is needed?
Round the item up to two 4 KiB units: 2 RCUs for one strongly consistent read per second. Eventual reads use half that. A 6 KiB ordinary write per second consumes 6 WCUs before index/transaction effects. GSIs support eventual reads; a hot partition is not solved merely by adding an index.
S3 copies recover two minutes behind, while the latest usable EBS snapshot is 20 hours old. Is RPO two minutes?
No. The workload depends on every required state store. Record the newest recovered write per store; EBS can dominate data loss. Faster DNS or extra web servers do not make an old snapshot newer.
A queue grows while CPU stays low. Which scaling signal is missing?
Inspect backlog per available worker and oldest-message age alongside processing latency and downstream limits. CPU-only scaling may miss I/O-bound work. Unlimited workers can overload the database; scaling must respect the bottleneck.
Objects are deleted after ten days. Is a lower archive storage price automatically cheaper?
No. Include minimum storage duration, retrieval, requests and object-size charges. Common minimum durations (AWS S3 pricing): Standard-IA / One Zone-IA 30 days, Glacier Instant / Flexible Retrieval 90 days, Deep Archive 180 days. Match retrieval time and retention before comparing unit price.
